## Чему ты научишься

- Хранить результат долгого счёта в `Rails.cache` и брать его оттуда.
- Строить ключ копии так, чтобы любая правка исходных книг делала её
  ненужной.
- Кешировать куски страницы и связывать их с тем, из чего они сделаны
  (`touch`).
- Приёму, который дороже синтаксиса: **копию не чистят — её перестают
  находить.** Ключ, в котором версия данных, устаревает сам, и спрашивать
  «а не пора ли почистить?» не нужно никогда.

Подробнее — в [`theory.md`](theory.md).

## Теория: ключ с версией

### `Rails.cache.fetch`

```ruby
Rails.cache.fetch(key) { summary(month) }
```

Нашлось по ключу — вернуть найденное. Не нашлось — исполнить блок,
положить результат под ключом и вернуть. В Rails 8 кеш — Solid Cache:
строки таблицы `solid_cache_entries` в той же базе. Копия переживает
перезапуск и видна всем процессам.

В проверках по умолчанию кеш выключен (`config.cache_store = :null_store` в
`config/environments/test.rb`). Проверка кеша на `:null_store` проверяет,
что кеша нет, — поэтому в этой серии кеш в проверках тот же, что на проде.

### Ключ знает версию

Вопрос не «когда чистить копию», а «как сделать, чтобы старую копию не
нашли». Ответ: положить в ключ версию того, из чего она сосчитана.

```ruby
books = [where(arrived_on: days), Acceptance.where(accepted_on: days), Disbursement.where(paid_at: window)]
Rails.cache.fetch(["summary", month, *books.map(&:cache_key_with_version)]) { summary(month) }
```

`cache_key_with_version` у выборки — «что за выборка» плюс «сколько в ней
строк и когда правили последнюю»:

```
deliveries/query-3f2a…-2-18920517000000
```

Один дешёвый запрос (`COUNT` и `MAX(updated_at)`) вместо долгого счёта.

| Что случилось в книге | `MAX(updated_at)` | `COUNT` | Копия |
|---|---|---|---|
| строку добавили | новее | больше | устарела |
| строку поправили | новее | тот же | устарела |
| строку убрали | **тот же** (если убрали не последнюю) | меньше | устарела |

Ключ только по времени последней правки не узнает об удалении — ровно о том,
что сделал конторщик Лэнга.

Старые копии остаются в таблице, пока их не вытеснит предел размера
(`max_size` в `config/cache.yml`). Их никто не найдёт: ключ другой.

### Копия строки

Страница книги поставок — таблица, строка на поставку. Строку можно хранить
копией:

```erb
<% cache delivery do %>
  <tr>…<td><%= delivery.acceptances.size %></td>…</tr>
<% end %>
```

Ключ такой копии — поставка с её версией (`updated_at`) и отпечатком
шаблона. Но в строке — квитанции и выплата, а это другие книги. Новая
квитанция не меняет `updated_at` поставки, и копия строки не устареет.

```ruby
class Acceptance < ApplicationRecord
  belongs_to :delivery, touch: true
end
```

`touch: true`: сохранив или удалив квитанцию, Rails обновит `updated_at` у
её поставки. Версия поставки другая — копия строки устарела. Этот приём
называют «матрёшкой»: копия внешнего куска устаревает, когда устаревает
любая вложенная.

## Проверка: ADA задаёт вопросы

```
[ADA · КАБЕЛЬ НАГАСАКИ]

```

**1.** ADA: «Почему не `expires_in: 1.hour`? Через час копия устареет сама».

<details><summary>Ответ</summary>

Через час. А квитанция пришла через пять минут, и следующие пятьдесят пять
казначейство читает сводку без неё. Срок годности — это обещание врать не
дольше часа.

Версия в ключе делает копию верной всегда: она живёт ровно до правки книги,
не минутой дольше и не минутой меньше. Срок годности имеет смысл как второй
предохранитель — если книгу правят мимо Rails, например SQL-запросом.
</details>

**2.** ADA: «В ключе — версии трёх книг. Выплату из ключа можно убрать:
выплаты бывают раз в день».

<details><summary>Ответ</summary>

Раз в день — значит, раз в день сводка будет показывать вчерашнюю сумму
выплат, пока её не вытеснит что-то ещё. Ключ копии — всё, от чего зависит
результат, без исключений «потому что редко».

Проверка простая: пройтись по блоку `summary` и выписать каждую книгу, в
которую он смотрит. Каждая — в ключе.
</details>

**3.** ADA: «Зачем `touch`? В копии строки можно указать ключом поставку
вместе с квитанциями: `cache [delivery, delivery.acceptances]`».

<details><summary>Ответ</summary>

Можно, и это будет верно. Но чтобы построить такой ключ, надо спросить
квитанции у базы — на каждой строке, на каждом чтении. Копия, ради которой
на каждой строке ходят в базу, экономит меньше, чем обещает.

`touch` переносит работу на запись: квитанция трогает поставку один раз, когда
её заводят, а чтение спрашивает только поставку.
</details>

## Разбор типичных ошибок

1. **`:null_store` в проверках.** Кеш «работает», потому что его нет.
2. **`:memory_store`.** Копия у каждого процесса своя и умирает с ним.
3. **Ключ без версий.** Первая копия — навсегда.
4. **Версия — только время последней правки.** Удаление не видно.
5. **Ключ без месяца.** Июнь показывает май.
6. **Ключ без одной из книг.** Выплата не меняет сводку.
7. **`expires_in` вместо версии.** Врёт до конца срока.
8. **Нет `touch`.** Строка поставки не видит новой квитанции.
9. **Одна копия на всю книгу.** Любая правка пересчитывает все строки.

книг — добавили, поправили, убрали — делает копию ненужной, и следующий
читатель видит новые числа. Строки книги поставок устаревают от квитанций и
выплат.
