# Теория — s06e04

## 1. «Ровно раз» не бывает

Работник исполняет записку так:

```
1. взять записку        (claimed)
2. сделать работу       (выплата легла)
3. отметить сделанной   (finished_at)
```

Между 2 и 3 — мгновение. Если работник умрёт в это мгновение, очередь не
знает, была ли работа: она видит только взятую записку без живого работника.
У неё два выбора:

| Очередь решает | Что обещает | Чем рискует |
|---|---|---|
| вернуть записку в готовые | **хотя бы раз** (at-least-once) | работу сделают дважды |
| выбросить записку | **не больше раза** (at-most-once) | работу не сделают вовсе |

Третьего нет. Solid Queue и GoodJob выбирают первое: потерять выплату хуже,
чем получить повтор. (Sidekiq без платной версии на жёстком падении
процесса теряет взятые записки — это второе.) «Ровно раз» (exactly-once)
— это «хотя бы раз» плюс задача, которой второй раз ничего не делает.

Повторы приходят не только от смерти работника:

- записку положили дважды — два запроса, две квитанции, двойной щелчок;
- чужая система ответила ошибкой, а работу на деле сделала (`s06e05`);
- два работника исполнили две записки об одном и том же одновременно.

## 2. Идемпотентность

**Идемпотентная операция** — та, которую можно применить сколько угодно раз с
тем же результатом, что и один раз. `x = 5` идемпотентно, `x += 5` — нет.
`PUT` и `DELETE` в HTTP обещаны идемпотентными, `POST` — нет (RFC 9110,
9.2.2).

Выплату делают идемпотентной ключом: у эффекта есть ключ, и эффект с этим
ключом бывает один.

```
выплата(поставка) — одна на поставку
```

### Как выбрать ключ

Спросить: **чего должно быть одно?** Не «по какому поводу работаем», а «что
не должно удвоиться».

| Кандидат | Одно ли его? |
|---|---|
| записка (`job_id`) | нет: вторая квитанция — вторая записка |
| квитанция | нет: квитанций на поставку может быть несколько |
| поставка | да: выплата за поставку одна |

Ключ, выбранный по конверту, закрывает повторы конверта и пропускает всё
остальное. Это ровно то, что делает казначейство: квитанция — документ,
повтор документа — тоже документ.

## 3. Почему не «а нет ли уже?»

```ruby
return if Disbursement.exists?(delivery: delivery)
Disbursement.create!(delivery: delivery, ...)
```

Два шага. Между ними — окно, в которое помещается второй работник с тем же
вопросом:

```
работник А: exists? → нет
работник Б: exists? → нет
работник А: create!
работник Б: create!       — вторая выплата
```

Это окно из `s04e04`, только теперь его открывают не два клерка, а два
потока `bin/jobs`. Закрывает его одно: уникальный индекс. База не положит
вторую строку, кто бы и когда бы её ни писал.

### `find_or_create_by` и `create_or_find_by`

| Метод | Порядок | Когда ломается |
|---|---|---|
| `find_or_create_by!` | найти → нет → создать | окно между «найти» и «создать»; с индексом второй получает `RecordNotUnique` |
| `create_or_find_by!` | создать → индекс отказал → найти | не ломается; цена — лишняя попытка записи, и индекс обязателен |

`create_or_find_by!` ловит `RecordNotUnique` внутри точки сохранения
(`SAVEPOINT`), так что внешняя транзакция переживает отказ. Два условия:
уникальный индекс на ключе и **никакой проверки уникальности в модели**:
`validates :uniqueness` спросит «а нет ли?» раньше индекса и поднимет
`RecordInvalid`, который `create_or_find_by!` не ловит.

### Особенность SQLite

На SQLite пишущая транзакция одна на всю базу (`BEGIN IMMEDIATE` в Rails 8):
второй работник ждёт, пока первый закончит. Поэтому `find_or_create_by!`
**внутри** транзакции здесь безопасен — второй работник найдёт строку
первого. На PostgreSQL при обычном уровне изоляции (read committed) оба
найдут «нет». Код, который верен на одной базе и неверен на другой, — плохой
код: выбирай тот, что верен везде.

## 4. Два эффекта — одна транзакция

У выплаты два эффекта: строка в книге выплат и телеграмма казначейству. Если
они ложатся порознь, между ними опять окно:

```
выплата легла
— свет погас —
повтор: выплата есть → «уже сделано» → телеграмма не уйдёт никогда
```

Решение — одна транзакция на оба. Оно работает, потому что «телеграмма» — это
три строки в одной базе: телеграмма в книге, записка в `solid_queue_jobs`,
её положение в `solid_queue_scheduled_executions` или `ready_executions`.
Транзакция кладёт их вместе с выплатой или не кладёт ничего.

Этот приём называют **transactional outbox** («исходящий ящик в транзакции»):
сообщение наружу не отправляют из транзакции, а кладут в таблицу той же
транзакцией, и отдельный работник отправляет его потом. С очередью в Redis
его пришлось бы строить руками — отдельной таблицей «к отправке». С Solid
Queue очередь и есть эта таблица.

`previously_new_record?` после `create_or_find_by!` отвечает: эту строку
создал этот вызов или нашёл готовую. Сообщает о выплате только тот, кто её
сделал.

## 5. Идемпотентность входа

Квитанции приходят телеграфом, и одна телеграмма может прийти дважды: повтор
линии, двойная доставка. У `acceptances` уникальный индекс на `(route,
line_number)` — ключ телеграммы. `Acceptance.receive!` — `create_or_find_by!`
по нему. Это второй ключ, у другого эффекта: «одна строка на телеграмму». У
выплаты ключ свой — поставка. Ключи не обязаны совпадать; каждый выбирают по
тому, чего должно быть одно **здесь**.

## 6. Чего эта серия не закрывает

- **повтор к чужой системе**: мы отдали телеграмму, линия её передала, ответ
  не дошёл — как не отдать второй раз — `s06e05`;
- **входящий повтор** — одна квитанция, дважды присланная линией, — `s06e06`;
- **`limits_concurrency`** в Solid Queue — не больше одной записки с данным
  ключом одновременно. Делает двойное исполнение реже; невозможным не
  делает: смерть работника остаётся.
