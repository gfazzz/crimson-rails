# Теория — s06e02

## 1. Где живёт записка

Очередь задач — это место, где записка ждёт работника. От того, где это
место, зависит всё остальное:

| Где записка | Что переживает | Что теряет |
|---|---|---|
| память процесса (`:async`) | ничего | всё при перезапуске |
| Redis (Sidekiq, Resque) | перезапуск конторы | то, что Redis не успел сохранить на диск |
| таблица базы (Solid Queue, GoodJob) | перезапуск, ночь, падение работника | ничего, что пережила база |

Rails 8 по умолчанию ставит Solid Queue: записка — строка в той же базе, где
лежат телеграммы. Одна база — одна резервная копия, одна транзакция
(`s06e01`, раздел 5), один набор ограничений.

## 2. Таблицы Solid Queue

```
solid_queue_jobs                  — сама записка: класс, аргументы, очередь, приоритет
  ├─ solid_queue_ready_executions     — готова к исполнению
  ├─ solid_queue_scheduled_executions — ждёт своего времени
  ├─ solid_queue_claimed_executions   — взята работником
  ├─ solid_queue_blocked_executions   — ждёт, пока освободится ограничение одновременности
  └─ solid_queue_failed_executions    — упала
solid_queue_processes             — кто сейчас работает: работники, диспетчеры, надзиратель
```

Положение записки — в какой из таблиц у неё строка. Сделанная записка
остаётся в `solid_queue_jobs` с `finished_at` — до очистки.

Жизнь записки:

```
perform_later ─┬─ сейчас ──────────────► ready ─┐
               └─ wait_until ─► scheduled ─┘    │ работник: claim
                    диспетчер переносит          ▼
                                             claimed ─┬─► finished_at
                                                      └─► failed
```

`claim` — одна транзакция: строки выбираются с блокировкой (`FOR UPDATE SKIP
LOCKED` там, где база умеет), переносятся во взятые и удаляются из готовых.
Два работника одну записку не возьмут.

## 3. Процессы `bin/jobs`

`bin/jobs` поднимает надзирателя (supervisor), и тот — остальных:

| Процесс | Что делает |
|---|---|
| работник (worker) | берёт готовые записки своих очередей и исполняет их в потоках |
| диспетчер (dispatcher) | раз в `polling_interval` переносит наступившие отложенные в готовые |
| надзиратель (supervisor) | следит, что процессы живы; записки умерших возвращает в готовые |

Каждый процесс раз в минуту отмечается в `solid_queue_processes` (heartbeat).
Процесс, который не отмечался дольше порога (по умолчанию пять минут),
считается умершим, и его взятые записки возвращаются в готовые. Так очередь
обещает «хотя бы раз»: записка не потеряется, но может исполниться второй
раз.

В разработке `bin/jobs` запускают рядом с сервером. На проде — так же, или
внутри Puma: `plugin :solid_queue` при `SOLID_QUEUE_IN_PUMA=1`
(`config/puma.rb`).

## 4. Очереди и работники

Очередь — строка `queue_name` в записке. Работник слушает список очередей:

```yaml
workers:
  - queues: telegraph        # только телеграф
    threads: 1
  - queues: [default, mail]  # две очереди, по порядку
    threads: 3
  - queues: "*"              # все очереди
```

Три правила, которые стоит проверять проверкой, а не глазами:

1. **У каждой очереди есть работник.** Записка в очереди, которую никто не
   слушает, не падает и не ругается — она просто лежит.
2. **Потоков столько, сколько выдержит то, к чему они ходят.** Один кабель —
   один поток. База отчётов — сколько даст пул соединений.
3. **Звёздочка слушает всё.** Работник с `"*"` пересекается со всеми
   остальными.

Потоков у работника больше одного — значит, задачи его очередей исполняются
одновременно. Пул соединений к базе (`pool` в `database.yml`) должен быть не
меньше числа потоков.

## 5. Приоритет

```ruby
queue_with_priority 0                     # всегда 0
queue_with_priority { arguments.first.urgent? ? 0 : 10 }   # по аргументам
DispatchJob.set(priority: 0).perform_later(t)              # на одну записку
```

Работник берёт из очереди записки по возрастанию приоритета, при равном — по
порядку постановки. В Solid Queue **меньшее — раньше**, как и в
Delayed::Job; в Resque приоритетов нет вовсе, в Sidekiq вместо них веса
очередей. Число без комментария в коде — ловушка для следующего, кто его
прочтёт: поэтому `TREASURY = 0`, `ROUTINE = 10`.

Приоритет работает внутри того, что работник берёт. Он не обгоняет записку в
другой очереди, если работник эту очередь не слушает.

## 6. Отложенный запуск

```ruby
DispatchJob.set(wait: 5.minutes).perform_later(t)
DispatchJob.set(wait_until: Time.zone.parse("08:00")).perform_later(t)
```

Записка ложится сразу, в `scheduled_executions`. Диспетчер делает её готовой
не раньше `scheduled_at` — и, возможно, чуть позже: на `polling_interval`.
Время открытия — это «не раньше», а не «ровно».

Время в `wait_until` — момент, а не «восемь часов». `Time.zone.local(…, 8)`
— восемь по часовому поясу приложения; `Time.utc(…, 8)` — восемь по
Гринвичу, во Владивостоке это пять вечера. Часовой пояс конторы задан в
`config/application.rb` (`config.time_zone`), и все сравнения с часами
станции делаются в нём: `time.in_time_zone.hour`.

## 7. Чего эта серия не закрывает

- **повтор после сбоя, пауза между попытками** — `s06e03`;
- **задача, исполненная дважды** — `s06e04`;
- **ограничение одновременности** (`limits_concurrency`) — одна записка на
  ключ за раз; упомянуто в таблицах и не нужно сезону: один поток телеграфа
  делает то же для одной очереди;
- **повторяющиеся задачи по расписанию** — `s06e10`.
