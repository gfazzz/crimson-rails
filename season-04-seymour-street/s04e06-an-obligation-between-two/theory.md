# Теория — s04e06

## 1. Два способа связать многих со многими

```ruby
has_and_belongs_to_many :companies     # таблица companies_consignments, два столбца
has_many :legs                          # обычная модель...
has_many :companies, through: :legs     # ...и цепочка через неё
```

Признак выбора один: **есть ли у связи собственные сведения.**

«Дорога участвовала» — сведений нет. «Участок номер два, сто девяносто миль» —
есть, и держать их в таблице из двух столбцов негде.

На практике `has_and_belongs_to_many` почти всегда преждевременен: сведения
появляются позже, и переделывать связь приходится на живых данных. Честный
случай для него ровно один — связь без сведений, которая такой и останется.

## 2. Промежуточная модель

Это обычная модель. У неё есть валидации, колбэки, свои правила и свои
индексы; она может быть найдена и показана сама по себе. Всё, что отличает её
от прочих, — две ссылки вместо одной.

```ruby
class Leg < ApplicationRecord
  belongs_to :consignment
  belongs_to :company
end
```

## 3. Составной индекс

```ruby
add_index :legs, %i[consignment_id position], unique: true
```

**Уникальна пара.** Ни `consignment_id`, ни `position` по отдельности не
уникальны, и это правильно.

**Порядок столбцов решает, что можно искать.** Индекс отсортирован по первому
столбцу, внутри него — по второму. Искать можно по началу этого порядка:

| Запрос | `[consignment_id, position]` |
|---|---|
| `WHERE consignment_id = ?` | годится |
| `WHERE consignment_id = ? AND position = ?` | годится |
| `WHERE position = ?` | не годится |
| `ORDER BY consignment_id, position` | годится |

Метафора, которая работает: телефонный справочник, отсортированный по фамилии,
потом по имени. Найти всех Смитов легко; найти всех Джонов — только просмотром
всего.

Отсюда правило: **первым идёт то, по чему ищут всегда**; дальше — то, что
сужает.

В модели паре соответствует:

```ruby
validates :position, uniqueness: { scope: :consignment_id }
```

И, как всегда в этом сезоне, `scope:` — вежливость, индекс — гарантия.

## 4. `through` и `source`

```ruby
has_many :legs
has_many :companies, through: :legs
```

`through:` не заводит новую связь. Он читает существующую по цепочке и
превращается в `JOIN`: «дороги этой перевозки» = «дороги её участков».

`source:` нужен, когда имя нашей связи не совпадает с именем связи на том
конце:

```ruby
has_many :carried_consignments, through: :legs, source: :consignment
```

Здесь `carried_consignments` ведёт к `Consignment`, но связь внутри `Leg`
зовётся `consignment` — Rails не догадается по имени и потребует подсказки.

Цепочка бывает длиннее двух звеньев (`through:` на связь, которая сама
`through:`), и это работает; читаемость при этом падает быстрее, чем растёт
удобство.

## 5. Область видимости у связи

```ruby
has_many :legs, -> { order(:position) }, dependent: :destroy, inverse_of: :consignment
```

Лямбда делает порядок частью самой связи: читать путь не по порядку
бессмысленно, а сортировка «на каждом вызове» забывается ровно там, где важна.

Так же добавляют условия (`-> { where(settled: false) }`), но тут стоит
помнить: связь с условием — это уже небольшая область видимости, и её
отсутствие в одном месте отчёта даёт другой ответ.

## 6. `dependent:` во второй раз

| | s04e05: дорога → перевозки | s04e06: перевозка → участки |
|---|---|---|
| имеют ли смысл в одиночку | да, это деньги | нет |
| решение | `:restrict_with_error` | `:destroy` |

Признак один и тот же, а ответы разные — в этом и смысл признака. «Что удобнее
удалить» ответа не даёт.

## 7. Чего эта серия не закрывает

- **N+1 при обходе цепочки** — `s04e07`: `consignment.legs` в цикле по
  перевозкам даёт запрос на каждую;
- **`counter_cache`** — сезон 5;
- **полиморфные связи** — в курсе не понадобятся;
- **ограничение «ровно один участок помечен головным»** — это уже
  частичный уникальный индекс, `s04e08`.
