# Теория — s04e07

## 1. Relation ленив

`where`, `order`, `limit`, `joins`, `includes`, `group` и всё, что возвращает
`ActiveRecord::Relation`, **не ходит в базу**. Relation копит условия и молчит.

Ленивость кончается там, где просят строки:

```
to_a  each  map  first  last  find_each  count  sum  pluck  exists?  any?
empty?  size (иногда)  inspect  интерполяция в строку
```

`size` — особый случай: у загруженного relation это `length` в памяти, у
незагруженного — `COUNT`. Это удобно и иногда неожиданно.

Отсюда `scope`:

```ruby
scope :unsettled, -> { where(settled: false) }
```

Лямбда обязательна. `scope :recent, where(sent_on: Date.current)` без неё
вычислится один раз — при загрузке класса, — и «сегодня» застынет на дне
выката.

И правило: **`scope` обязан вернуть relation.** Если внутри есть условие,
возвращающее `nil`, цепочка сломается там, где её продолжат. Пишут
`-> { code.present? ? where(...) : all }`.

## 2. N+1

```ruby
Consignment.all.each { |c| c.legs.each { |l| l.company.code } }
```

1 запрос за перевозками, N за участками, N×M за дорогами. На трёх строках —
десять запросов, на сорока одной тысяче — сто двадцать три тысячи.

Три вещи, которые делают N+1 опасным:

- **ответ правильный.** Ничего не падает и не врёт;
- **на отладочных данных его нет.** Десять строк — десять запросов, быстро;
- **он растёт линейно.** Значит, обнаруживается ровно тогда, когда исправлять
  дороже всего.

Определение, годное для проверки: **число запросов растёт с числом строк.**
Так это и измеряют — не временем, а счётом обращений.

## 3. Четыре способа взять связь

| Способ | SQL | Загружает объекты | Годится для |
|---|---|---|---|
| `preload(:legs)` | отдельный `SELECT ... WHERE consignment_id IN (…)` | да | чтения |
| `eager_load(:legs)` | один `LEFT OUTER JOIN` | да | чтения + отбора по связи |
| `includes(:legs)` | сам выбирает `preload` или `eager_load` | да | по умолчанию |
| `joins(:legs)` | `INNER JOIN` | **нет** | отбора |

`includes` переключается на `eager_load`, когда видит условие по связанной
таблице (`references` подсказывает ему это явно).

Самая частая ошибка — `joins` там, где потом читают связь: отбор стал
правильным, N+1 остался. Вторая по частоте — `includes` там, где связь нужна
только в `where`: загружены объекты, которых никто не посмотрит.

Цепочка тоже собирается: `includes(legs: :company)`.

## 4. Считает база

```ruby
Leg.where(consignment_id: relation.select(:id)).group(:company_id).sum(:miles)
```

Один запрос, одна строка на дорогу. Тот же свод объектами — сорок одна тысяча
объектов, созданных, сложенных и выброшенных.

Агрегаты: `count`, `sum`, `average`, `minimum`, `maximum`; с `group` каждый
возвращает хеш.

`relation.select(:id)` внутри `where` подставляется **подзапросом**. Если
написать `relation.pluck(:id)`, relation загрузится, и в запрос уедет список
из сорока одной тысячи чисел — некоторые базы такой `IN` просто не примут.

## 5. Спрашивать дёшево

| Вместо | Лучше | Почему |
|---|---|---|
| `count > 0` | `exists?` | `LIMIT 1` вместо счёта всей таблицы |
| `all.map(&:reference)` | `pluck(:reference)` | один столбец вместо всех граф |
| `all.each` на большой таблице | `find_each` / `in_batches` | не держит всё в памяти |
| `where(...).first` в цикле | `where(id: […])` один раз | тот же N+1 |
| `order(...).first` | `minimum` / `first` с индексом | без сортировки всего |

`select(:a, :b)` берёт часть граф и возвращает объекты — но обращение к
незагруженному полю бросает `MissingAttributeError`, и это лучше, чем тихий
`nil`.

## 6. Как измерить

```ruby
ActiveSupport::Notifications.subscribe("sql.active_record") do |*, payload|
  puts payload[:sql]
end
```

То же делает `ActiveRecord::Base.logger` в development и панель запросов в
`rack-mini-profiler`. Для тестов есть `assert_queries_count` (Rails 7.2+) и
гем `n_plus_one_control`, проверяющий ровно то свойство, о котором эта
серия: число запросов не растёт с числом строк.

Библиотека проверок этого сезона (`support/check.rb`) считает запросы тем же
способом — через уведомления.

## 7. Индексы и планы

Индексы этот сезон уже ставил (`s04e04`, `s04e06`) — здесь они начинают
работать по второму назначению: ускорять отбор. Посмотреть, пользуется ли ими
база:

```ruby
Consignment.unsettled.explain
```

Правило, которое стоит запомнить раньше остальных: **сначала посчитайте
запросы, потом смотрите план.** Полтораста тысяч быстрых запросов остаются
полутораста тысячами запросов.

## 8. Чего эта серия не закрывает

- **кеширование** (`Rails.cache`, кеш фрагментов, `counter_cache`) — сезон 6;
- **пагинация и курсоры** — сезон 5;
- **`find_in_batches` на миллионах строк, блокировки при обходе** — `s04e10`;
- **оконные функции, CTE, сырой SQL** — за пределами курса; `Arel` и
  `sanitize_sql` стоит знать, но в `ledger` они не понадобятся.
