## Чему ты научишься

- Складывать отборы, не ходя в базу: `scope`, ленивость, где именно она
  кончается.
- Видеть N+1 и убирать его `includes`.
- Считать своды базой, а не Ruby: `group`, `sum`, `pluck`.
- Спрашивать дёшево: `exists?` вместо `count.positive?`.
- Приёму, который дороже синтаксиса: **N+1 даёт правильный ответ.** Он не
  ломается и не падает — он растёт. Поэтому его находят не на отладке, а через
  год, когда строк стало сорок тысяч.

Подробнее — в [`theory.md`](theory.md).

## Теория: три запроса вместо ста двадцати трёх тысяч

### Отбор — это кусок запроса

```ruby
scope :unsettled, -> { where(settled: false) }
scope :sent_between, ->(from, to) { where(sent_on: from..to) }

Consignment.unsettled.sent_between("1891-08-01", "1891-08-31")
```

Всё это — `ActiveRecord::Relation`, а не строки. Relation **ленив**: он
собирает условия и молчит, пока кто-нибудь не попросит строки. Поэтому куски
складываются, и в базу уходит один запрос вместо трёх.

Ленивость кончается там, где просят: `to_a`, `each`, `map`, `first`, `count`,
`pluck`, `any?`, интерполяция в строку, `inspect` в консоли. Последнее —
причина, по которой в консоли всё кажется не ленивым.

### N+1

```ruby
Consignment.all.each do |record|        #   1 запрос
  record.legs.each do |leg|             # + N запросов
    leg.company.code                    # + N × M запросов
  end
end
```

На трёх перевозках это десять запросов и незаметно. На сорока одной тысяче —
сто двадцать три тысячи и час.

Главное про N+1: **он даёт правильный ответ.** Не падает, не врёт, не
ломается. Он просто растёт с числом строк — поэтому его не находят на отладке.

```ruby
Consignment.includes(legs: :company).each { ... }   # 3 запроса, всегда 3
```

`includes` забирает связанные записи заранее, одним запросом на связь.

| Способ | Что делает | Когда |
|---|---|---|
| `includes` | Rails выбирает сам: `preload` или `eager_load` | по умолчанию |
| `preload` | отдельный запрос на каждую связь | связанные не нужны в `where` |
| `eager_load` | один запрос с `LEFT JOIN` | по связанным идёт отбор |
| `joins` | `INNER JOIN` без загрузки объектов | связь нужна для отбора, а не для чтения |

`joins` не загружает объекты — и это его смысл. Если после `joins` обратиться
к связи, N+1 вернётся.

### Считает база

```ruby
Leg.where(consignment_id: relation.select(:id)).group(:company_id).sum(:miles)
# => { 1 => 48, 2 => 380, 3 => 380 }
```

Один запрос, одна строка на дорогу. Тот же свод, собранный объектами, — это
сорок одна тысяча объектов, которые создадут, сложат и выбросят.

`relation.select(:id)` подставляется в запрос **подзапросом**, а не списком из
сорока одной тысячи чисел: relation остаётся ленивым до самого конца.

### Спрашивать дёшево

```ruby
Consignment.unsettled.exists?        # SELECT 1 ... LIMIT 1
Consignment.unsettled.count > 0      # COUNT(*) по всей ведомости
Consignment.pluck(:reference)        # только нужный столбец
Consignment.all.map(&:reference)     # все графы, потом одна
```

Разница не в красоте. `exists?` останавливается на первой строке; `count`
читает все.

**1.** ADA: «`Consignment.unsettled` в консоли показал строки. Значит relation
не ленив?»

<details><summary>Ответ</summary>

Ленив. Строки показала консоль.

`irb` зовёт `inspect` у всего, что ему вернули, а `inspect` у relation просит
первые строки, чтобы их напечатать. То же самое делает отладочная печать в
коде.

Признак ленивости надёжнее смотреть по журналу запросов: пока `SELECT` в нём
не появился, базу никто не спрашивал.
</details>

**2.** ADA: «`includes` или `joins`?»

<details><summary>Ответ</summary>

Зависит от того, нужны ли связанные объекты.

`joins` подшивает таблицу к запросу и **не загружает** её объекты: он для
отбора. `includes` загружает: он для чтения.

Частая ошибка — `joins` там, где потом читают связь: отбор стал правильным, а
N+1 остался. И обратная — `includes` там, где связь нужна только в `where`:
лишние объекты, которые никто не посмотрит.
</details>

**3.** ADA: «Как понять, что в коде N+1, если он не падает?»

<details><summary>Ответ</summary>

Посчитать запросы на двух разных объёмах.

Если на трёх строках запросов десять, а на двенадцати — сорок, это N+1. Если
на обоих три — нет. Число запросов, растущее с числом строк, и есть
определение.

Так устроена и проверка этой серии: она гоняет свод дважды и сравнивает не
время, а количество обращений.
</details>

## Разбор типичных ошибок

1. **Запрос в цикле.** Правильный ответ, растущая цена.
2. **`joins` там, где потом читают связь.** N+1 остался.
3. **`includes` там, где связь нужна только в `where`.** Лишние объекты.
4. **`map` вместо `pluck`.** Все графы ради одной.
5. **`count.positive?` вместо `exists?`.** Счёт всей ведомости ради ответа
   «да».
6. **`relation.to_a` посреди цепочки.** Ленивость кончилась, следующий отбор
   пошёл по Ruby.
7. **Свод, собранный объектами.** Сорок одна тысяча объектов, которые
   выбросят.
8. **`select(:id)` заменён списком идентификаторов.** Подзапрос превратился в
   `IN (…)` на сорок тысяч чисел.
9. **`scope` с лямбдой, вычисленной один раз** (`where(sent_on: Date.current)`
   без `->`). Дата застынет на времени загрузки класса.
10. **Отбор, возвращающий `nil`.** `scope` обязан вернуть relation: иначе
    цепочка ломается там, где её продолжат.
