# Теория — s04e08

## 1. Четыре места, где может стоять правило

| Где | Кого касается | Что говорит |
|---|---|---|
| форма / интерфейс | того, кто заполняет | «так нельзя» до отправки |
| валидация модели | пришедших через модель | поле и причину |
| ограничение схемы | всех, кто пишет в базу | «нет» |
| тип столбца | всех | «это не то» |

Сезон четвёртый — про третью строку. Первые две объясняют, третья
гарантирует, и подменять одну другой нельзя ни в какую сторону.

## 2. `CHECK`

```ruby
add_check_constraint :consignments, "pence > 0", name: "consignments_pence_positive"
remove_check_constraint :consignments, name: "consignments_pence_positive"
```

Условие на значения **строки**. Проверяется при каждой вставке и обновлении.

Что `CHECK` умеет:

- сравнения и арифметику по столбцам той же строки: `pence > 0`,
  `ends_on >= starts_on`;
- принадлежность набору: `role IN (0, 1, 2)`;
- функции без побочных эффектов: `length(code) BETWEEN 2 AND 4`.

Чего не умеет:

- смотреть в другие таблицы (для этого внешний ключ);
- смотреть в другие строки той же таблицы («не более трёх на дорогу» — это уже
  блокировка, `s04e09`);
- пользоваться `now()` и прочим изменчивым: условие должно оставаться верным
  для строки, которая лежит без движения.

**Имя обязательно.** Безымянному Rails сгенерирует `chk_rails_<хеш>`; в
сообщении об отказе окажется именно оно. По имени ограничение ищут в коде,
снимают и меняют.

SQLite поддерживает `CHECK`; Rails реализует `add_check_constraint` через
перестроение таблицы — на больших таблицах это важно помнить (`s04e10`).
MySQL проверяет `CHECK` с версии 8.0.16, раньше молча игнорировал.

## 3. Частичный индекс

```ruby
add_index :legs, :consignment_id, unique: true, where: "role = 0"
```

Индексируются только строки, подходящие под условие. Отсюда два следствия:
индекс меньше, и уникальность держится **только в этой части**.

Где это нужно постоянно:

| Задача | Условие |
|---|---|
| ровно один принявший на перевозку | `role = 0` |
| мягкое удаление: код свободен после удаления | `discarded_at IS NULL` |
| один основной адрес на человека | `primary = true` |
| одна активная подписка | `state = 'active'` |

Поддержка: PostgreSQL и SQLite — да; MySQL — нет, там ту же задачу решают
вычисляемым столбцом, который равен ключу для «активных» и `NULL` для прочих
(в `UNIQUE` `NULL` не конфликтует сам с собой).

В модели частичной уникальности соответствует валидация с условием:

```ruby
validates :role, uniqueness: { scope: :consignment_id, conditions: -> { collected } },
                 if: :collected?
```

`conditions:` сужает запрос, которым валидация ищет занятость; `if:` — случаи,
когда её вообще спрашивают.

## 4. `enum`

```ruby
enum :role, { collected: 0, hauled: 1, delivered: 2 }
```

Rails 7+ принимает такой синтаксис (раньше — `enum role: { ... }`). Даёт:

```ruby
leg.collected?     leg.hauled!     Leg.delivered     Leg.roles
```

**Не даёт ничего в базе.** В столбце лежит число; `update_all(role: 7)`
положит семёрку, и после этого `leg.role` бросит
`ArgumentError`, а `Leg.collected` промолчит. Поэтому рядом ставят `CHECK`
или пользуются родным `ENUM` PostgreSQL.

Число или строка:

| | число | строка |
|---|---|---|
| место | меньше | больше |
| сравнение | быстрее | медленнее |
| переименование | правка кода | миграция данных |
| читаемость в `SELECT` | нет | да |

Курс берёт число, потому что роль переименуют скорее, чем начнут читать
`SELECT` глазами. Оба варианта честны.

Осторожно с `default:` у `enum` и с изменением чисел задним числом: значение
уже лежит в строках, и сдвиг нумерации переименует их все разом.

## 5. Умолчание

Умолчание выбирают не по «самому частому», а по правилу:

> **Умолчание не должно нарушаться самим фактом второй строки.**

Если ролей три и «принял» бывает по одной на перевозку, то умолчание «принял»
означает, что вторая строка ломает правило до того, как кто-то что-то решил.
Умолчание берут среди значений, не ограниченных по числу.

Ещё два соображения про умолчания:

- умолчание в схеме действует на всех, умолчание в модели — на пришедших
  через неё (`s04e02`);
- умолчание, добавленное к существующему столбцу, не меняет старых строк. Для
  них нужен отдельный проход (`s04e10`).

## 6. Исключающие ограничения (для общего развития)

PostgreSQL умеет `EXCLUDE USING gist` — «никакие две строки не пересекаются по
диапазону дат». Это то, чего не выразить ни `CHECK` (смотрит только свою
строку), ни уникальным индексом (равенство, а не пересечение).

В `ledger` не понадобится, но знать о нём стоит: половина задач вида
«не должно быть двух брони на одно время» решается именно так, а не
блокировками.

## 7. Чего эта серия не закрывает

- **правила про несколько строк сразу** («не более трёх активных») —
  `s04e09`, через блокировку и транзакцию;
- **добавление условия на непустую таблицу** — `s04e10`: `CHECK` упадёт на
  первой же старой строке, и лечится это `validate: false` плюс отдельным
  проходом;
- **триггеры** — за пределами курса; почти всё, ради чего их ставят, делается
  ограничениями и транзакциями.
