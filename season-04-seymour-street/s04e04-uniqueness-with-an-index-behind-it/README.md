## Чему ты научишься

- Ставить уникальный индекс и понимать, что он единственная гарантия.
- Видеть, где именно ломается `validates :uniqueness`.
- Заводить запись так, чтобы двойной вызов не заводил вторую.
- Различать «вежливость» и «гарантию» и не подменять одну другой.
- Приёму, который дороже синтаксиса: **не смотреть перед тем, как положить.**
  Смотреть бессмысленно: ответ устаревает к моменту записи. Кладут и
  разбираются с отказом.

Подробнее — в [`theory.md`](theory.md).

## Теория: ограничитель

### Где ломается валидация

```ruby
validates :code, uniqueness: true
```

Что она делает на самом деле:

```
SELECT 1 FROM companies WHERE code = 'GNR' LIMIT 1   -- занято?
-- ... здесь проходит время ...
INSERT INTO companies (code, ...) VALUES ('GNR', ...)
```

Два запроса. Между ними — окно, в которое помещается чужой `INSERT`. Оба
процесса спросили, обоим ответили «свободно», оба записали. Ни одна из
валидаций не ошиблась: на момент вопроса ответ был верным.

Это не редкость и не «теоретическая гонка». Это две вкладки, двойной щелчок по
кнопке, повтор запроса после таймаута, две задачи очереди, два сервера
приложения.

### Индекс

```ruby
add_index :companies, :code, unique: true
```

Индекс не спрашивает. Он отказывает — на уровне записи, атомарно, для всех
сразу: для модели, для консоли, для `insert_all`, для скрипта переноса и для
соседней системы. Отказ приходит как `ActiveRecord::RecordNotUnique`.

Заодно он ускоряет поиск по этому столбцу, но здесь это побочный эффект.

**Нужны обе.** Валидация называет поле и говорит «занято», пока читатель ещё у
формы. Индекс отказывает в тот единственный раз, когда валидация не успела.
Убрать можно ровно ту, чью работу вы готовы не делать.

### Уникальность поверх приведения

```ruby
normalizes :code, with: ->(code) { code.strip.upcase }
add_index :companies, :code, unique: true
```

Индекс сравнивает то, что лежит в столбце: `GNR` и `gnr` для него разные
значения. Поэтому приведение к общему виду — **часть** уникальности, а не
украшение: оно решает, что именно считать «тем же самым».

Другой способ — индекс по выражению (`LOWER(code)`) или столбец с
регистронезависимым сравнением (`citext` в PostgreSQL). Оба годятся; главное —
выбрать один и знать, какой.

### Завести, не заводя второй

```ruby
def self.register(code:, name:)
  create!(code:, name:)
rescue ActiveRecord::RecordInvalid, ActiveRecord::RecordNotUnique
  find_by!(code:)
end
```

Порядок обратный привычному. «Сначала посмотреть, потом завести» между двумя
запросами не держится: посмотрели оба, не нашли оба, завели оба. Поэтому
пробуют завести и разбираются с отказом — отказ приходит после записи и потому
не устаревает.

Отказов два, и пережить надо оба: `RecordInvalid` — валидация успела,
`RecordNotUnique` — не успела.

В Rails есть готовые `find_or_create_by` (ищет, потом заводит — та же гонка) и
`create_or_find_by` (заводит, ловит отказ индекса). Второй правильнее, но у
него есть подвох: **валидация уникальности перехватывает конфликт раньше
индекса**, и тогда `create_or_find_by` возвращает несохранённый объект вместо
найденного. Вместе они не работают, и это стоит знать до, а не после.

**1.** ADA: «`validates :uniqueness` стоит. Нужен ли индекс?»

<details><summary>Ответ</summary>

Нужен, и это не «на всякий случай».

Валидация делает `SELECT`, потом `INSERT`. Между ними окно, в которое
помещается чужая запись. Один процесс в один поток эту дыру не покажет никогда
— она открывается ровно тогда, когда нагрузка выросла.

Признак, по которому это решают: **что вы будете делать, если дубль
появится?** Если «исправим руками» — можно жить с валидацией. Если «Палата
возьмёт плату дважды» — нужен индекс.
</details>

**2.** ADA: «Индекс поставлен. Нужна ли валидация?»

<details><summary>Ответ</summary>

Нужна — для читателя.

Индекс отказывает исключением. Без валидации пользователь получит пятисотую
вместо формы с подписью «этот номер уже заведён», а в журнале приложения
окажется `RecordNotUnique` там, где должна была быть обычная проверка ввода.

Правило: валидация — для сообщения, индекс — для гарантии. `rescue
RecordNotUnique` при этом всё равно нужен: он ловит то единственное попадание
в окно.
</details>

**3.** ADA: «`find_or_create_by` в двух процессах. Что получится?»

<details><summary>Ответ</summary>

Две записи — если за ним нет индекса. Исключение — если есть.

`find_or_create_by` это буквально «посмотреть, потом завести», то есть та же
гонка, только написанная в одну строку. С индексом она превращается в
`RecordNotUnique`, и его надо поймать.

Поэтому порядок обратный: завести и разобраться с отказом.
</details>

## Разбор типичных ошибок

1. **Валидация без индекса.** Единственная ошибка этой серии, которая
   действительно стоит денег.
2. **Индекс без `unique: true`.** Ускоряет и ничего не держит.
3. **Индекс на другом столбце.** Уникален не тот, кто уникален по существу.
4. **Индекс без валидации.** Пятисотая вместо формы с ошибкой.
5. **Приведение к общему виду снято.** `GNR` и `gnr` для индекса разные.
6. **`find_or_create_by` как средство от дублей.** Та же гонка, в одну
   строку.
7. **`create_or_find_by` рядом с валидацией уникальности.** Валидация
   перехватывает конфликт, и возвращается несохранённый объект.
8. **Ловить только `RecordNotUnique`.** Почти всегда придёт `RecordInvalid`.
9. **Ловить только `RecordInvalid`.** В тот единственный раз придёт другое.
10. **`rescue` вокруг всего блока.** Поймано будет и то, чего не ждали.
