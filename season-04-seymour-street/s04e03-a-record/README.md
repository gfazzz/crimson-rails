## Чему ты научишься

- Различать `new` и `save`, `save` и `save!`, `update` и `update!`.
- Писать валидации, которые называют поле и причину.
- Приводить введённое к общему виду до проверки — `normalizes`.
- Читать, что в записи изменилось: `changed?`, `_was`, `saved_change_to_*`.
- Приёму, который дороже синтаксиса: **модель обязана отказать первой.** Если
  до базы дошла запись, которую она отвергнет, читатель получит падение
  вместо формы с ошибкой — и не узнает, что исправлять.

Подробнее — в [`theory.md`](theory.md).

## Теория: тот, кто смотрит до базы

### Объект и запись

```ruby
company = Company.new(name: "Мидлендская дорога", code: "MID")
company.new_record?   # true — в базе ещё ничего нет
company.save          # true, и теперь есть
company.persisted?    # true
company.id            # номер назначила база
```

`new` собирает объект в памяти; в базу ходит `save`, и только он. `create` —
это `new` плюс `save` одной строкой.

### Пара с восклицательным знаком

| Без `!` | С `!` |
|---|---|
| `save` → `true`/`false` | `save!` → бросает `RecordInvalid` |
| `update` → `true`/`false` | `update!` → бросает |
| `create` → объект (может быть несохранённый) | `create!` → бросает |

Это не «строгий и нестрогий вариант», а два разных случая. **Без `!`** — когда
есть кому показать ошибку: форма, интерфейс, ответ по API. **С `!`** — когда
показать некому: скрипт, задача очереди, миграция данных. Там тихий `false`
хуже падения, потому что его никто не прочтёт.

### Валидации

```ruby
validates :name, presence: true
validates :code, presence: true, length: { in: 2..4 }
validates :pence, numericality: { only_integer: true, greater_than: 0 }
```

Валидация делает две вещи, которых база не делает: **называет поле** и
**объясняет причину**. Результат — в `errors`: `company.errors[:name]`,
`company.errors.full_messages`.

`numericality` без `allow_nil` отвергает и пустое значение — «не число».
Ставить рядом ещё и `presence` значит жаловаться дважды об одном.

И главное, что про валидации надо знать: **они не гарантия.** Их не зовут
`insert_all`, `update_all`, `delete_all`, консоль, скрипт переноса и соседняя
система. Поэтому за правилом, которое должно держаться всегда, обязано стоять
ограничение в схеме — `s04e04` и `s04e08` про это.

### Приведение до проверки

```ruby
normalizes :code, with: ->(code) { code.strip.upcase }
```

`normalizes` (Rails 7.1+) приводит значение **до** валидации и перед записью —
и, что важнее, перед поиском: `Company.find_by(code: " mid ")` найдёт `MID`.

Порядок «привести, потом проверить» не вкусовой: иначе правило пришлось бы
писать на все написания сразу, а в реестре код один.

### Что изменилось

```ruby
company.name = "Мидлендская железная дорога"
company.changed?              # true
company.changed               # ["name"]
company.name_was              # прежнее значение
company.save!
company.saved_change_to_name? # true
```

На этом держатся колбэки, частичное обновление (`UPDATE` только изменённых
столбцов) и добрая половина отладки «почему запись не сохранилась».

## Проверка: ADA задаёт вопросы

```
[ADA · ПОДВАЛ]
ТРИ ВОПРОСА.
```

**1.** ADA: «`save` вернул `false`. Что произошло в базе?»

<details><summary>Ответ</summary>

Ничего. Запроса не было.

`save` сначала гоняет валидации; не прошли — он возвращает `false`, не дойдя
до `INSERT`. Причина лежит в `errors`, и если её не показать, читатель решит,
что сохранилось.

Отсюда практическое правило: `save` без проверки результата — это `save!`,
написанный неправильно.
</details>

**2.** ADA: «`validates :code, length: { in: 2..4 }` стоит, `presence` — нет.
Что будет с пустым кодом?»

<details><summary>Ответ</summary>

Зависит от того, дописали ли `allow_nil: true`.

Без него `length` отвергнет `nil` («too short»), и модель откажет — неудобно
сформулировав, но откажет. С `allow_nil: true` запись пройдёт валидацию,
дойдёт до базы и упадёт там на `NOT NULL` — `ActiveRecord::NotNullViolation`
вместо формы с ошибкой.

Это и есть правило «модель обязана отказать первой»: не потому, что база не
справится, а потому, что её отказ нечитаем.
</details>

**3.** ADA: «Нужна ли валидация, если в схеме уже стоит `null: false`?»

<details><summary>Ответ</summary>

Нужна — они делают разное.

Схема не даёт лечь строке и молчит о причинах. Валидация называет поле и
причину, но её обходит всякий, кто пришёл не через модель.

Дублированием это выглядит только на бумаге. На практике одна отвечает за
читателя, другая — за данные, и убирать можно ровно ту, чью работу вы готовы
не делать.
</details>

## Разбор типичных ошибок

1. **`save` без проверки результата.** Тихий `false`, и никто не узнал.
2. **`save!` там, где есть форма.** Падение вместо сообщения об ошибке.
3. **`allow_nil: true` рядом с `null: false` в схеме.** Модель пропускает,
   база роняет.
4. **`presence` рядом с `numericality`.** Две жалобы об одном.
5. **Валидация вместо ограничения.** Правило, которое обязано держаться
   всегда, живёт только в модели.
6. **Приведение после проверки** (`before_save` вместо `normalizes`).
   Проверяется одно, сохраняется другое, а поиск не находит.
7. **Умолчание, продублированное в модели.** Второе место, где записано то же
   самое, и рано или поздно они разойдутся.
8. **`update_attribute`.** Пишет мимо валидаций; почти всегда это не то, что
   имели в виду.
9. **Валидация уникальности.** Её время — следующая серия, и там же
   выяснится, чего она не умеет.
10. **Правила, растащенные по колбэкам.** `before_save`, который «чинит»
    данные, прячет ошибку вместо того, чтобы её назвать.
