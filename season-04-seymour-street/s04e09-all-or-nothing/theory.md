# Теория — s04e09

## 1. Проводка

```ruby
Settlement.transaction do
  ...
end
```

Всё внутри ложится вместе или не ложится вовсе. Четыре свойства, за которые
проводку и держат (ACID):

| | Что значит | Что делать, когда не хватает |
|---|---|---|
| атомарность | целиком или никак | ради неё всё и пишется |
| согласованность | ограничения верны и до, и после | ставить ограничения (`s04e05`, `s04e08`) |
| изоляция | параллельные проводки не видят половин | блокировки (§4) и уровни изоляции |
| долговечность | записанное переживёт падение | настройка базы, не приложения |

`Settlement.transaction` и `ActiveRecord::Base.transaction` — одно и то же:
проводка живёт на **соединении**, а не на классе. Писать имя класса стоит
ради читаемости, а не потому, что это ограничивает проводку его таблицей.

### Три ловушки

**`return`, `break`, `throw` изнутри блока.** До Rails 6.1 они молча
откатывали проводку; сейчас `return` откатывает и выпускает управление, что
почти всегда не то, чего хотели. Выход из проводки — это её конец.

**`ActiveRecord::Rollback`.** Откатывает и **не летит дальше**. Это
единственный способ сказать «отменить» без исключения наружу; любое другое
исключение откатывает и летит.

```ruby
transaction do
  ...
  raise ActiveRecord::Rollback if nothing_to_do   # тихо
end
# сюда попадём, и ничего не записано
```

**Вложенная проводка — не проводка.** По умолчанию внутренний
`transaction` присоединяется к внешнему: его «конец» ничего не фиксирует, а
его откат откатывает всё. Отдельную просят явно:

```ruby
transaction(requires_new: true) { ... }   # SAVEPOINT
```

### Работа после фиксации

Письмо, задача очереди, запрос в чужую систему внутри проводки — почти всегда
ошибка: проводка откатится, а письмо уже ушло. Для этого есть

```ruby
after_commit :notify, on: :create
```

и симметричный `after_rollback`. Правило простое: **в проводке — только то,
что база умеет откатить.**

## 2. Идемпотентность

Операция идемпотентна, если второй вызов даёт тот же итог, а не второй.

```ruby
record = find_or_initialize_by(company_id: company_id, period: period)
record.pence = pence
record.save!
```

Почему это важнее защиты от повторного нажатия: повтор приходит не от кнопки.
Оборвалась связь, и клиент повторил запрос. Задача очереди упала после записи
и вернулась (очереди дают «хотя бы один раз», а не «ровно один»). Оператор
запустил пересчёт второй раз, потому что первый «завис».

Три способа её получить:

| Способ | Когда |
|---|---|
| поиск по естественному ключу (`find_or_initialize_by`) | у строки есть пара, которая её определяет |
| `upsert_all` / `INSERT ... ON CONFLICT` | строк много, объекты не нужны |
| ключ идемпотентности от клиента | у операции нет естественного ключа (платёж) |

Все три держатся на одном: **за ключом стоит уникальный индекс.** Без него
`find_or_initialize_by` — это «посмотреть, потом завести» из `s04e04`, со
всем тем же окном между.

`присваивание` против `+=`: пересчёт **заменяет** сумму, а не прибавляет к
прежней. Прибавление не идемпотентно по определению.

## 3. Оптимистичная блокировка

Столбец `lock_version`, который Rails ведёт сам:

```sql
UPDATE settlements SET pence = 200, lock_version = 4
WHERE id = 7 AND lock_version = 3
```

Обновилось ноль строк — значит, кто-то успел раньше; Rails бросает
`ActiveRecord::StaleObjectError`.

- Никто никого не ждёт, лишних запросов нет.
- Имя столбца — договор: `lock_version`. Другое имя задаётся
  `self.locking_column = "..."`, но по умолчанию Rails просто ничего не
  включит и ничего не скажет.
- `update_all`, `increment_counter` и сырой SQL **проходят мимо** — счётчик
  ведёт модель, а не база.
- Столкновение нельзя «не заметить»: `StaleObjectError` надо где-то поймать и
  что-то показать человеку. Обычно — перечитать и дать сравнить.

Годится там, где столкновения редки, а ждать дорого: формы, долгое
редактирование, правка через интерфейс.

## 4. Пессимистичная блокировка

Строку берут под блокировку и держат до конца проводки:

```ruby
record.with_lock do          # transaction + lock!
  raise AlreadyPaid if record.paid?
  record.update!(state: :paid)
end
```

`lock!` — это `reload(lock: true)`, то есть `SELECT ... FOR UPDATE`.
**Перечитывание важнее блокировки:** без него проверка смотрит в копию,
снятую минуту назад, и отвечает на вопрос «было ли оплачено минуту назад».

Блокировка живёт только внутри проводки — вне её `FOR UPDATE` снимается сразу
после запроса и не значит ничего. Поэтому `with_lock`, а не `lock!` сам по
себе.

Варианты, которые стоит знать:

| Ruby | SQL | Смысл |
|---|---|---|
| `lock: true` | `FOR UPDATE` | ждать, пока освободится |
| `lock: "FOR UPDATE NOWAIT"` | то же | не ждать, упасть сразу |
| `lock: "FOR UPDATE SKIP LOCKED"` | то же | пропустить занятые (очереди) |
| `lock: "FOR SHARE"` | `FOR SHARE` | читателям можно, писателям нет |

Цена: пока строка занята, остальные ждут. Две проводки, берущие две строки в
разном порядке, дают **взаимную блокировку** (deadlock); база убивает одну из
них, и приложение обязано уметь повторить. Лечится дисциплиной: строки берут
всегда в одном порядке.

## 5. Какую выбрать

| | оптимистичная | пессимистичная |
|---|---|---|
| ждут ли | нет | да |
| при столкновении | ошибка второму | второй ждёт |
| цена | повторить действие | занятая строка |
| видно ли в схеме | столбец | ничего |
| где | формы, редактирование | деньги, остатки, номера |

Признак: **дорого ли потерять работу, сделанную между чтением и записью.**
Если человек полчаса правил текст — дорого, и лучше отвергнуть запись
(оптимистичная). Если между чтением и записью три строки кода про деньги —
дешевле подождать (пессимистичная).

## 6. Уровни изоляции (для общего развития)

Проводка изолирована не абсолютно. Уровень задаётся при её открытии:

```ruby
transaction(isolation: :serializable) { ... }
```

| Уровень | Что ещё может случиться |
|---|---|
| `read_committed` (умолчание PostgreSQL) | одно и то же чтение дважды даёт разное |
| `repeatable_read` (умолчание MySQL) | «фантомы»: новых строк не видно, но запись может упасть |
| `serializable` | ничего; за это платят падениями и повторами |

`serializable` не отменяет обязанности повторять: база вправе отвергнуть
проводку, которую не смогла расставить в порядок. Поэтому в реальном коде чаще
берут `read_committed` плюс блокировку в том одном месте, где решение
принимается по прочитанному.

## 7. Про SQLite

У SQLite нет блокировок строк: на запись блокируется вся база. Отсюда:

- `with_lock` даёт проводку и перечитывание, но не блокировку строки;
- `SELECT ... FOR UPDATE` не поддерживается и молча игнорируется;
- `SQLite3::BusyException` — это «база занята», а не «строка занята»;
  лечится `timeout` в `database.yml`.

Для курса этого достаточно: код, написанный по дисциплине «читать под
блокировкой», верен и на PostgreSQL, где блокировка настоящая. Обратное
неверно — код, написанный «как получилось на SQLite», на PostgreSQL ломается
не сразу, а под нагрузкой.

## 8. Чего эта серия не закрывает

- **Проводка на две базы** — двухфазная фиксация; в Rails её нет, и это
  правильно. Вместо неё — outbox: запись о намерении ложится в ту же
  проводку, а отправляет её отдельный процесс.
- **Очереди и «ровно один раз»** — его не бывает; бывает «хотя бы один раз»
  плюс идемпотентность.
- **Изменение живой таблицы под нагрузкой** — `s04e10`.
