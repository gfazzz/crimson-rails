# Теория — s04e01

## 1. Что такое миграция

Миграция — обычный файл Ruby с номером в имени:

```
db/migrate/20260818093000_create_companies.rb
```

Четырнадцать цифр — **версия**. Rails держит список прогнанных версий в самой
базе, в служебной таблице `schema_migrations`, и сравнивает его с папкой
`db/migrate`. Всё, чего в списке нет, прогоняется по возрастанию версии.

Отсюда следует то, что удивляет первым: **прогнанный файл Rails больше не
читает никогда.** Не «не перечитывает до перезапуска» — никогда. Его версия
уже в списке.

Поэтому правило про правку прогнанной миграции — не стиль и не вкусовщина.
Правка дойдёт ровно до одного человека: того, кто заводит базу с нуля после
неё. У остальных схема останется прежней при том же коде, и разойдутся они
молча.

Единственное исключение: миграция, которую никто, кроме вас, не прогонял и
которая не ушла дальше вашей машины. Тогда `db:rollback`, правка,
`db:migrate`.

## 2. `[8.0]` в объявлении класса

```ruby
class CreateCompanies < ActiveRecord::Migration[8.0]
```

Это версия **правил**, по которым читается миграция. Rails меняет умолчания:
скажем, в 5.0 `t.references` перестал по умолчанию создавать внешний ключ,
а в 7.1 поменялось поведение `add_column` с `default`. Миграция, написанная
под 5.0, обязана вести себя как под 5.0 — иначе прошлое перестанет
воспроизводиться, а вместе с ним и продакшен, собранный из миграций с нуля.

Отсюда практическое следствие: номер в скобках не «обновляют». Он про то,
когда файл написан.

## 3. Схема — это не описание, а факт

После прогона Rails сам пишет `db/schema.rb`:

```ruby
ActiveRecord::Schema[8.0].define(version: 2026_08_18_100000) do
  create_table "companies", force: :cascade do |t|
    t.string "name", null: false
    t.date "registered_on"
    ...
  end
end
```

Три вещи про этот файл:

- **он слепок, а не источник.** Правка руками живёт до следующего прогона;
- **он идёт в репозиторий.** По нему `db:schema:load` (и `db:prepare` на
  чистой машине) собирает базу за один шаг, не прогоняя семьсот миграций;
- **`version:`** — версия последней прогнанной миграции. По ней видно, отстаёт
  ли схема.

Альтернатива — `config.active_record.schema_format = :sql` и `structure.sql`.
Нужна там, где в базе есть то, чего Ruby-описание не выражает: триггеры,
хранимые функции, частичные индексы со сложным условием, специфические типы
PostgreSQL. Цена — файл, который человек уже не читает.

## 4. `change` и обратимость

```ruby
def change
  create_table :companies { ... }
end
```

`change` — одно описание на оба направления. Rails знает обратное для
обратимых действий: `create_table` ↔ `drop_table`, `add_column` ↔
`remove_column`, `add_index` ↔ `remove_index`, `rename_column` ↔ обратное
переименование.

Не обратимо само по себе: `execute` с сырым SQL, `remove_column` без указания
типа (Rails не знает, какой столбец восстанавливать), любой перенос данных.
Там пишут `up`/`down` — или оборачивают необратимую часть:

```ruby
def change
  reversible do |direction|
    direction.up   { execute "..." }
    direction.down { execute "..." }
  end
end
```

Если обратного действия не существует, честный ответ — бросить
`ActiveRecord::IrreversibleMigration`. Это лучше, чем `down`, который делает
вид.

Откат проверяют:

```bash
bin/rails db:rollback          # на ступень вниз
bin/rails db:rollback STEP=3   # на три
bin/rails db:migrate:redo      # вниз и обратно вверх
```

## 5. Ограничение против валидации

| | `null: false` в схеме | `validates :presence` в модели |
|---|---|---|
| кого касается | всех, кто ходит в базу | только тех, кто пришёл через модель |
| что делает | не даёт строке лечь | объясняет человеку, что не так |
| когда срабатывает | в базе, на запросе | в приложении, до запроса |
| обходится | никак | консолью, `insert_all`, `update_all`, соседней системой |

Нужны обе, и это не дублирование: у них разные работы. Валидация — интерфейс,
ограничение — гарантия.

Практическое следствие для всего сезона: **если гарантия нужна, она должна
быть в схеме.** Проверка серий это и проверяет — вставкой сырым SQL.

## 6. Типы столбцов и SQLite

`t.string` (короткий текст), `t.text` (длинный), `t.integer`, `t.bigint`,
`t.float`, `t.decimal`, `t.boolean`, `t.date`, `t.datetime`, `t.binary`,
`t.json`, `t.references`.

SQLite относится к типам мягче остальных: у него динамическая типизация со
«сродством» столбца, и он **не проверяет** длину `varchar`. Что он держит
по-настоящему и на чём стоит сезон:

- `NOT NULL`;
- `UNIQUE` (в том числе составной);
- `FOREIGN KEY` — при включённом `PRAGMA foreign_keys`, который Rails
  включает сам;
- `CHECK`.

Чего не стоит ждать от SQLite: проверки длины строки, богатых типов
PostgreSQL, параллельной записи. Всё, что серии проверяют, переносится на
PostgreSQL без изменений — обратное неверно, и об этом стоит помнить, когда
курс кончится.

Отдельно про `t.timestamps`: это `created_at` и `updated_at`, которые Rails
ведёт сам. Восстановить их задним числом нечем, поэтому их ставят сразу и
почти всегда.

## 7. Генераторы

```bash
bin/rails generate migration CreateCompanies name:string code:string
bin/rails generate migration AddRegisteredOnToCompanies registered_on:date
bin/rails generate migration RemoveCodeFromCompanies code:string
bin/rails generate model Company name:string code:string
```

Генератор разбирает имя: `CreateXxx` → `create_table`, `AddXxxToYyy` →
`add_column`, `RemoveXxxFromYyy` → `remove_column` (с типом, чтобы миграция
осталась обратимой).

Это удобство, а не обязанность: миграция — обычный файл, и написать его
руками ничем не хуже. В курсе заготовки лежат в `starter/` — так проверка не
зависит от того, в какую минуту вы её сгенерировали.

## 8. Команды, которые стоит различать

| Команда | Что делает | Когда |
|---|---|---|
| `db:migrate` | прогнать непрогнанное, переписать `schema.rb` | после написания миграции |
| `db:rollback` | откатить последнюю | передумали |
| `db:migrate:status` | список версий и их состояние | «почему не применилось» |
| `db:prepare` | завести базу и загрузить схему; если база есть — прогнать миграции | чистая установка |
| `db:schema:load` | собрать базу из `schema.rb`, минуя миграции | быстрая сборка с нуля |
| `db:migrate:reset` | снести базу и прогнать миграции с нуля | база в непонятном состоянии |
| `db:seed` | наполнить данными из `db/seeds.rb` | демо-данные |

`db:reset` = `db:drop db:setup`; данные теряются, и это его работа, а не
побочный эффект.

**Одна ловушка, на которую попадают все.** На пустой базе `db:migrate` не
прогоняет миграции — он **загружает `db/schema.rb`** и отмечает все версии как
прогнанные. Логика разумная: собрать базу из слепка быстрее, чем из семисот
миграций. Но если схема пустая или устарела, `db:drop db:create db:migrate`
вернёт ровно то состояние, из которого вы выбирались. Прогнать именно
миграции: `db:migrate:reset`.

## 9. Чего эта серия не закрывает

- **уникальность** — `s04e04`: обязательность есть, единственности нет;
- **связи и внешние ключи** — `s04e05`;
- **`CHECK` и частичные индексы** — `s04e08`;
- **миграции на живых данных**: блокировки, backfill батчами,
  `disable_ddl_transaction!`, необратимость на проде — финал сезона,
  `s04e10`;
- **несколько баз** (Rails 8 из коробки заводит `cache`, `queue`, `cable`) —
  сезон 6.
