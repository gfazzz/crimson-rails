# Теория — s04e10

## 1. Два вопроса к любой миграции

Первый задают все: **что она делает со схемой.**

Второй задают редко, и именно он решает, выкатится ли она: **что она делает с
тем, что уже лежит в таблице.**

| Вопрос | На пустой базе | На таблице в миллион строк |
|---|---|---|
| сколько идёт | миллисекунды | минуты и часы |
| кого держит | никого | всех, кто пишет в таблицу |
| что если упала | ничего | половина работы сделана |
| проверена ли | нет | да |

Миграция, прошедшая только на пустой базе, не проверена. Это не придирка: в
тестовой базе, собранной из `schema.rb`, данных нет вовсе, и ни одна миграция
там не падает по данным.

## 2. Три шага и их порядок

Одно изменение на живой таблице всегда разваливается на три миграции:

```
1. схема        добавить столбец — пустым, необязательным
2. данные       заполнить, разобрать, подвести под правило
3. ограничение  объявить правило базе
```

Почему не одной:

- проводка держится столько, сколько идёт самый долгий шаг;
- упавший третий шаг откатывает первые два, и заполнение надо начинать
  сначала;
- `null: false` в той же миграции проверяется на данных, которых в момент
  добавления столбца ещё не было;
- шаг с данными хочется **перезапускать**, а шаг со схемой — нет.

**Откат идёт в обратном порядке:** снять ограничение, данные не трогать,
убрать столбец.

То же правило действует и при выкатке в несколько машин: между шагами живут
и старый код, и новый. Отсюда ещё одно следствие — **столбец не переименовывают
одной миграцией.** Заводят новый, пишут в оба, переносят, читают из нового,
убирают старый. Четыре выкатки вместо одной.

## 3. Столбец на непустую таблицу

```ruby
add_column :entries, :voided_at, :datetime                # всегда
add_column :entries, :voided_at, :datetime, null: false   # откажет
add_column :entries, :state, :integer, null: false, default: 0   # см. ниже
```

Про `default:` есть страх, который старше, чем нужно: до PostgreSQL 11
умолчание, добавленное к столбцу, переписывало всю таблицу — то есть
блокировало её на время, пропорциональное её размеру. С PG 11 умолчание
пишется в каталог, и добавление мгновенно.

Что **не** изменилось: умолчание не заполняет старые строки значением, если
они уже существовали до него в nullable-виде, и любое реальное заполнение
остаётся отдельной работой. Делает её проход, а не `default:`.

Отдельно стоит помнить про блокировки самого `ALTER TABLE`: он берёт
`ACCESS EXCLUSIVE` и ждёт, пока освободятся все читающие. Долгий `SELECT`
перед ним выстроит за собой очередь из всех остальных. Поэтому на живой базе
`ALTER TABLE` пускают с `lock_timeout` и повтором, а не «когда получится».

## 4. Проход по данным

```ruby
Entry.where(voided_at: nil).where.not(id: survivors)
     .in_batches(of: 500) { |batch| batch.update_all(voided_at: now) }
```

| Способ | Запросов на 100 000 строк | Памяти |
|---|---|---|
| `all.each` | 100 001 | вся таблица в объектах |
| `find_each` | ~101 + 100 000 | порция |
| `update_all` одним | 1 | нисколько, но держит всё |
| `in_batches` + `update_all` | ~400 | порция |

`find_each` и `in_batches` — родственники: первый отдаёт записи по одной,
второй — отношения порциями. Для записи нужен второй: он позволяет писать
одним запросом на порцию.

Оба идут **по `id`, по возрастанию** (`WHERE id > ?`), а не `OFFSET`. Отсюда
важное: они не совместимы со своим `order`, и в этом их сила — `OFFSET` на
большом смещении заставляет базу заново пройти всё пропущенное.

### Мимо модели

```ruby
class VoidDuplicateDockets < ActiveRecord::Migration[8.0]
  class Entry < ActiveRecord::Base
    self.table_name = "entries"
  end
```

Миграция — запись о прошлом; модель — код настоящего. Через год и через пять
миграцию прогонят на пустой базе при заведении окружения, и к тому времени
настоящая модель:

- обрастёт валидациями, которые отвергнут старые строки;
- обрастёт колбэками, которые полезут в таблицы, появившиеся позже;
- получит `default_scope`, из-за которого половина строк не найдётся;
- или исчезнет вместе с таблицей — и миграция упадёт на `NameError`.

Своя модель на три строки живёт в файле миграции и не меняется никогда, ровно
как сама миграция. То же касается констант приложения: в миграции пишут
число или строку, а не `Entry::VOID_REASONS[:duplicate]`.

### Перезапускаемость

Отбор считают **заново на каждом заходе**:

```ruby
Entry.where(voided_at: nil)...     # сделанное само выпадает из отбора
```

Тогда шаг, оборванный посередине, при повторном запуске доделывает работу, а
запущенный дважды — не находит её вовсе. Противоположность — список
идентификаторов, собранный один раз до прохода: после обрыва он описывает
состояние, которого уже нет.

## 5. `disable_ddl_transaction!`

Rails оборачивает каждую миграцию в проводку — там, где база это умеет
(PostgreSQL и SQLite умеют; MySQL **нет**: `ALTER TABLE` там фиксируется сам
по себе, и половина миграции остаётся половиной).

Снимают обёртку в двух случаях:

1. **Долгий проход по данным.** Проводка на миллион строк держит миллион.
2. **`CREATE INDEX CONCURRENTLY`** на PostgreSQL — его нельзя выполнить
   внутри проводки:
   ```ruby
   disable_ddl_transaction!
   def change
     add_index :entries, :docket, algorithm: :concurrently
   end
   ```
   Обычный `CREATE INDEX` блокирует запись в таблицу на всё время построения.
   `CONCURRENTLY` не блокирует, но идёт вдвое дольше и **может упасть**,
   оставив нерабочий индекс (`indisvalid = false`), который надо снять и
   построить заново.

Цена одна и та же: «всё или ничего» больше нет. Поэтому у миграции без
проводки два требования вместо одного — она должна быть перезапускаемой, и
она должна делать что-то одно.

## 6. Ограничение задним числом

Индекс или `CHECK` ложится, только если данные ему уже соответствуют.
Порядок: **сначала разобрать, потом объявить.**

Как разбирать — вопрос к заказчику, а не к разработчику. «Оставить раннюю» и
«оставить позднюю» — разные деньги; «удалить» и «отметить» — разная история.

Если лишние строки остаются в таблице, уникальность нужна не по всей таблице,
а по её живой части:

```ruby
add_index :entries, %i[docket position], unique: true,
          where: "voided_at IS NULL", name: "index_entries_on_live_leg"
```

Имя обязательно: то, которое Rails придумает сам, совпадёт с именем обычного
индекса по той же паре.

На PostgreSQL есть приём в два шага и для `CHECK`:

```ruby
add_check_constraint :entries, "miles > 0", name: "entries_miles_positive",
                     validate: false          # действует на новые строки
# проход по старым
validate_check_constraint :entries, name: "entries_miles_positive"
```

Первый шаг быстрый и берёт слабую блокировку; второй читает таблицу, но не
мешает писать. То же для внешних ключей (`add_foreign_key ..., validate: false`
и `validate_foreign_key`). Смысл один: правило и данные подводят друг к другу
в два шага.

## 7. Обратимость шага с данными

Схему этот шаг не менял — откатывать нечего. Данные откатом не возвращаются:
«снять все отметки» вернуло бы и те, что поставлены руками после.

Отсюда `def down; end` — пустой, и это не лень:

| Вариант | Что будет при `db:rollback` до нуля |
|---|---|
| `def down; end` | проходит; данные не восстановлены, и это честно |
| `raise IrreversibleMigration` | откат до нуля невозможен вовсе |
| «снять все отметки» | сотрёт и ту работу, которую делали не миграцией |

Восстановление данных — это резервная копия, а не миграция. Обратимость,
которую обязана держать миграция, — обратимость **схемы**.

## 8. Чего эта серия не закрывает

- **Выкатка в несколько машин** и совместимость старого кода с новой
  схемой — это Kamal и следующий сезон.
- **Перенос между базами** и онлайн-инструменты вроде `pt-online-schema-change`
  и `gh-ost` — за пределами курса; знать стоит, что они существуют и зачем.
- **Разделение таблиц** (партиционирование) — там те же три шага, но
  умноженные на число разделов.
