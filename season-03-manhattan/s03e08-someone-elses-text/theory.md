# Теория — s03e08

## 1. Откуда берётся чужой текст

«Чужой» здесь — не «злой». Чужой текст это всякий текст, который написали не
вы: запись поста, имя приёмщика, название станции, ссылка из справочника,
заголовок страницы, параметр адреса, содержимое поля формы, ответ конторы.

До этой серии страница показывала то, что мы же в неё и набрали, — и разницы
между разметкой и данными не было, потому что автор был один. Как только
данные пришли из конторы, авторов стало двое, и один из них вам не знаком.

Правило, из которого следует остальное:

> **Разметку пишет тот, кто пишет разметку. Данные — это текст.**

## 2. Два места, где текст перестаёт быть текстом

Разметка попадает в страницу в двух видах, и обращаются с ними по-разному.

**Содержимое элемента.**

```js
node.innerHTML = item.text;   // текст разбирается как разметка
node.textContent = item.text; // текст остаётся текстом
```

`textContent` не «экранирует» — он вообще не разбирает. Строка `<b>` попадает
в дерево пятью символами, а не элементом. Разница видна сразу: после
`textContent` у узла ноль детей, чем бы его ни заполнили.

Рядом стоят `insertAdjacentHTML`, `outerHTML`, `document.write` и
`element.setHTMLUnsafe` — это всё тот же `innerHTML` с другого конца.

**Значение атрибута.** Здесь `textContent` не помогает, потому что атрибут —
не текст, а указание.

```js
link.setAttribute("href", item.source);  // "javascript:…" — это код
img.setAttribute("src", item.photo);     // "onerror" ждёт своего часа
node.setAttribute("style", item.style);  // чужой стиль поверх вашего
```

Опасны не все атрибуты, а те, по которым браузер что-то делает: `href`, `src`,
`action`, `formaction`, `srcdoc`, `style`, всё семейство `on*`. Их значения
проверяют — по-разному для каждого, потому что смысл у них разный.

## 3. Образец в разметке: `<template>`

```html
<template id="entry-template">
  <li>
    <p data-part="text"></p>
    <p class="hand"><span data-part="hand"></span> <a data-part="source" hidden></a></p>
  </li>
</template>
```

```js
const node = template.content.firstElementChild.cloneNode(true);
node.querySelector("[data-part='text']").textContent = item.text;
```

Что делает `<template>` и чего не делает:

- содержимое **разбирается** при загрузке страницы — синтаксические ошибки
  видно сразу, а не при первой записи;
- содержимое **не показывается** и не исполняется: картинки не грузятся,
  скрипты не запускаются, `querySelector` по странице внутрь не заглядывает;
- содержимое лежит в `template.content` — отдельном документе
  (`DocumentFragment`), и оттуда его **клонируют**: `cloneNode(true)` без
  аргумента `true` скопирует пустую оболочку, а без клонирования первая же
  запись унесёт образец с собой.

Зачем это, если можно `createElement`. Затем, что разметка строки
оказывается в разметке — рядом со всей остальной разметкой, где её правит
тот, кто правит разметку, а не тот, кто правит код. Проверка этой серии
дописывает в образец свою метку и смотрит, доехала ли она до строки: если нет
— строку собрали в другом месте.

## 4. Почему «почистить» чужой текст — не решение

Соблазн очевидный: выкинуть из текста всё, что похоже на разметку.

```js
text.replace(/<[^>]*>/g, "");   // так не делают
```

Три возражения, и каждого хватает.

**Это порча.** Пост передал «состав 7 < состава 8» — и потерял половину
фразы. Данные принадлежат автору данных.

**Это не работает.** `<img src=x onerror=…` без закрывающей скобки, `<<b>b>`,
кодировки, которых вы не ждали. Всякая чистка разбирает разметку хуже, чем
браузер, потому что браузер разбирает её двадцать лет и умеет прощать.

**Это не там.** Опасен не текст, а место, куда его кладут. Один и тот же текст
в `textContent` безвреден, а в `href` — нет.

Чистка нужна ровно в одном случае: когда чужая **разметка** должна остаться
разметкой (комментарий с курсивом и ссылками). Тогда её разбирают настоящим
разбором и собирают заново по списку разрешённого — этим занимаются
библиотеки вроде DOMPurify, и писать такое самому не нужно.

## 5. Список разрешённого

```js
const SAFE = new Set(["http:", "https:", "mailto:", "tel:"]);

export function safeHref(value, base = "http://localhost/") {
  const address = String(value ?? "").trim();
  if (address === "") return null;
  if (address.startsWith("#") || address.startsWith("/")) return address;
  try {
    const parsed = new URL(address, base);
    return SAFE.has(parsed.protocol) ? parsed.href : null;
  } catch {
    return null;
  }
}
```

Два решения, которые здесь приняты.

**Список разрешённого, а не запрещённого.** Запрещённое — это перечень того,
что уже придумали: `javascript:`, `data:`, `vbscript:`. Список разрешённого
не нужно дополнять, когда придумают следующее.

**Разбор, а не сравнение строк.** `new URL` приводит адрес к нормальному виду:
убирает пробелы и управляющие символы, приводит схему к нижнему регистру,
разрешает относительный адрес относительно базы. Поэтому
`«  JaVaScRiPt:alert(1)»` не проходит, а `«posts/14»` — проходит.

И третье, уже про страницу: негодный адрес не прячут, а **снимают**. Атрибут,
оставшийся в дереве, однажды покажут.

## 6. Форма записи

```js
export function entry({ id, state = "sent", hand = null, text = "", source = null, chalk = false }) {
  return { id: String(id), state, hand, text, source, chalk: Boolean(chalk) };
}
```

Разбор по именам — это не удобство записи, а граница. `{ ...item }` пропускает
в состояние всё, что прислала контора, включая поля, о которых не
договаривались; отрисовка потом разложит их по атрибутам, потому что отрисовке
неоткуда знать, какие из них наши.

Та же мысль в Rails зовётся strong parameters, и по той же причине: `permit`
перечисляет разрешённое.

## 7. Где это в Rails

ERB экранирует вывод по умолчанию:

```erb
<%= entry.text %>          <%# текст останется текстом %>
<%== entry.text %>         <%# а вот это — нет %>
<%= raw entry.text %>      <%# и это %>
<%= entry.text.html_safe %> <%# и это, и это опаснее всего %>
```

`html_safe` не делает строку безопасной — он объявляет её таковой. Это пометка
для шаблона, а не проверка, и слово «safe» в её имени стоило отрасли дорого.

Ссылки Rails проверяет сам: `link_to name, user_input` пропускает
`javascript:` через `sanitize`, а `Rails.application.config.action_view
.sanitized_allowed_tags` — тот же список разрешённого, только для тегов.

В сезоне 4 это встретится снова: `t()` с интерполяцией, `sanitize` в помощниках
и `content_tag`, который собирает разметку за вас именно затем, чтобы вы не
собирали её строкой.

## 8. Чего эта серия не закрывает

Чужой текст — половина разговора. Вторая половина в том, что браузер выполняет
не только разметку:

- **CSP** (`Content-Security-Policy`) — заголовок, который запрещает исполнять
  то, чего не было в разметке. Он не заменяет `textContent`, а страхует его;
- **чужой origin** — `<iframe sandbox>`, `rel="noopener"` у ссылок в новое
  окно, `crossorigin` у скриптов;
- **CSRF** — запрос, который делает не читатель, а чужая страница от его
  имени; Rails закрывает его меткой в форме, и в сезоне 4 это будет видно;
- **то, что в адресе** — параметры страницы это тоже чужой текст, и в
  `s03e10` адрес станет состоянием.
