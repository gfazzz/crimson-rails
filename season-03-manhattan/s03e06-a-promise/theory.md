# Теория — s03e06

## 1. Три исхода

```
pending    ещё не решилось
fulfilled  разрешилось значением
rejected   отклонилось причиной
```

Переход происходит **один раз**: разрешённое обещание больше не изменится, и
второй `resolve` ничего не сделает. Отсюда спокойствие: результат можно
запросить сколько угодно раз и в любой момент — даже спустя минуту после того,
как он появился.

Третий исход — не ошибка. Обещание, которое так и не решилось, не бросает
ничего, не попадает в `catch` и не оставляет следа. Оно просто висит, и всё,
что его ждёт, ждёт вместе с ним.

## 2. Чтение

```js
promise.then(onFulfilled, onRejected);
promise.then(onFulfilled).catch(onRejected).finally(always);

try {
  const answer = await promise;
} catch (error) {
  …
} finally {
  …
}
```

`then` возвращает **новое** обещание — потому цепочки и работают. Что бы
обработчик ни вернул, оно станет значением следующего звена; что бы он ни
бросил — станет причиной отказа.

`await` — та же цепочка сверху вниз. Он приостанавливает свою функцию, а не
страницу: браузер продолжает отвечать на события.

Две мелочи, на которых спотыкаются:

```js
async function f() { return 1; }         // вернёт обещание, не 1
[1, 2].forEach(async (x) => await g(x)); // forEach не ждёт: обещания потеряны
```

Во втором случае нужен `for … of` (по очереди) или `map` + `Promise.all`
(разом) — но не `forEach`.

## 3. Создание

```js
new Promise((resolve, reject) => {
  const timer = setTimeout(() => reject(new Error("вышло время")), 2000);
  wire(entry).then(
    (answer) => { clearTimeout(timer); resolve(answer); },
    (error) => { clearTimeout(timer); reject(error); },
  );
});

Promise.resolve(value);   уже разрешённое
Promise.reject(error);    уже отклонённое
```

`new Promise` нужен там, где источник не умеет в обещания: таймеры, старые
интерфейсы с обратными вызовами, события. Оборачивать в него то, что уже
вернуло обещание, — лишнее.

Внутри исполнителя опасно писать `async`: брошенное в нём исключение уйдёт в
никуда, а не в `reject`.

## 4. Срок

Срок ограничивает **ожидание**, а не работу. Запрос продолжится, линия
ответит, и ответ никому не понадобится. Настоящая отмена — `AbortController`
(`s03e07`).

```js
const timer = setTimeout(() => reject(new LineError("не ответила вовремя")), ms);
```

Готовый способ, если он есть под рукой:

```js
await Promise.race([work, new Promise((_, reject) => setTimeout(reject, ms, new Error("срок")))]);
```

и совсем короткий, из недавних: `AbortSignal.timeout(ms)` — он и срок задаёт,
и отменяет по-настоящему, если источник умеет слушать сигнал.

## 5. Своя ошибка

```js
export class LineError extends Error {
  constructor(message, { id, cause } = {}) {
    super(message, { cause });
    this.name = "LineError";
    this.id = id === undefined ? null : String(id);
  }
}
```

Зачем свой класс: по нему видно, чей это отказ, и в нём есть место для того,
что к отказу относится. `instanceof` при этом работает — а сравнение строк с
`error.message` не работает никогда.

`cause` (с 2021 года) хранит исходную ошибку. Без него приходится выбирать
между «своё сообщение» и «настоящая причина»; с ним есть и то и другое.

## 6. Комбинаторы

| | Что возвращает | Когда |
|---|---|---|
| `Promise.all` | массив значений | все успешны; при первом отказе — отказ |
| `Promise.allSettled` | массив `{status, value \| reason}` | все решились, как бы ни решились |
| `Promise.race` | первый решившийся | успех или отказ — что придёт первым |
| `Promise.any` | первый успешный | отказ, только если отказали все |

Выбор по смыслу: «без каждого нельзя» — `all`; «нужен отчёт по каждому» —
`allSettled`; «кто первый» — `race`; «хоть кто-нибудь» — `any`.

**Параллельно против по очереди:**

```js
for (const e of entries) await ask(e);              // сумма сроков
await Promise.allSettled(entries.map(ask));         // максимум из сроков
```

Разница не в стиле. Шесть запросов по две секунды — это двенадцать секунд
против двух.

Когда по очереди всё-таки правильно: следующий запрос зависит от ответа
предыдущего, или сервер не выдерживает залпа. Второе лечат ограничением числа
одновременных, а не полным отказом от параллельности.

## 7. Промежуточные результаты

`allSettled` отдаёт всё разом — то есть ждёт самого медленного. Если
результаты нужны по мере поступления, о них сообщают изнутри:

```js
entries.map(async (entry) => {
  try {
    const answer = await ask(entry);
    onSettled({ id: answer.id, state: "sent" });
    return answer;
  } catch (error) {
    onSettled({ id: String(entry.id), state: "failed", reason: error.message });
    throw error;
  }
});
```

Важно сообщать **один раз** на запись: подписчик применяет ответ к состоянию,
и второе сообщение перепишет то, что уже поправили.

## 8. Микрозадачи

```js
console.log("1");
setTimeout(() => console.log("4"));
Promise.resolve().then(() => console.log("3"));
console.log("2");
```

Порядок: 1, 2, 3, 4. Обработчики обещаний — **микрозадачи**: они выполняются
после текущего куска кода, но раньше таймеров и раньше отрисовки.

Практическое следствие: `await` не даёт браузеру перерисовать страницу.
Бесконечная цепочка микрозадач подвешивает вкладку так же надёжно, как цикл
`while (true)`.

## 9. Ошибки, о которых не узнают

```js
confirmShift();                 // ✘
confirmShift().catch(report);   // ✔
```

Отклонённое обещание без обработчика попадает в `unhandledrejection` (браузер)
или роняет процесс (Node). В обоих случаях — не там, где причина, и часто
через минуты после.

Обратная крайность — `catch`, который глотает:

```js
try { await ask(); } catch {}   // ✘ ошибка была, следа нет
```

Правило: ловят там, где есть что с ошибкой сделать. Если сделать нечего —
сообщают читателю или дают ей подняться выше.
