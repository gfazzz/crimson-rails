- Отличать `target` от `currentTarget` и знать, зачем это различие.
- Делегировать: один слушатель выше вместо ста ниже.

## Теория: событие

### Путь события

Событие не случается «на узле». Оно проходит путь от корня документа до цели и
обратно: сверху вниз (погружение), на цели, снизу вверх (всплытие).

```
document → body → ol#entries → li → p     погружение
                                     p    цель
p → li → ol#entries → body → document     всплытие
```

Слушатель на любом узле пути услышит событие, начавшееся на любом потомке. Это
ровно петля Дарнелл: щёлкает у всех, кто на линии.

```js
node.addEventListener("click", handler);         // на всплытии
node.addEventListener("click", handler, true);   // на погружении
```

Всплывают почти все события; не всплывают `focus`, `blur`, `load`, `error`
(у них есть всплывающие двойники `focusin` и `focusout`).

### Объект события

```js
register.addEventListener("click", (event) => {
  event.target;         // на чём началось — абзац внутри записи
  event.currentTarget;  // где слушают — сам журнал
  event.type;           // "click"
  event.preventDefault();   // отменить действие по умолчанию
  event.stopPropagation();  // не пускать дальше по линии
});
```

Различие `target` и `currentTarget` — это и есть позывной. Слушают на линии,
а кому адресовано — спрашивают у события.

### Делегирование

```js
register.addEventListener("click", (event) => {
  const entry = event.target.closest("li[data-id]");
  if (!entry || !register.contains(entry)) return;
  …
});
```

Три строки, и каждая нужна: `closest` поднимается от места нажатия вверх до
записи (нажали по абзацу внутри — значит нажали по записи); `!entry` — нажали
мимо; `contains` — запись нашлась, но из другого места страницы, что бывает,
когда слушают на `document`.

Что это даёт: **записи, которой не было при загрузке, ничего не нужно** — она
появилась и уже работает, потому что работает линия, а не узел.

Что теряется при обратном подходе: сто записей — сто слушателей; список
перерисовали — слушателей нет, и ошибки тоже нет.

### Пропускать то, что и без тебя что-то значит

```js
if (event.target.closest("a, button, input, select, textarea")) return;
```

Внутри записи может оказаться ссылка, и у неё своё дело. Обработчик записи
обязан её пропустить — иначе одно нажатие сделает две вещи.

### `preventDefault` и `stopPropagation` — разное

| | Что отменяет | Когда уместно |
|---|---|---|
| `preventDefault()` | действие браузера: переход, отправку, прокрутку | когда есть чем заменить |
| `stopPropagation()` | дальнейший путь события | почти никогда |

`preventDefault` без замены — молча сломанная страница: нажал и ничего.
`stopPropagation` рвёт линию: слушатели выше перестают слышать, и виноватого
ищут долго.

Отдельно: `return false` в обработчике, повешенном через `addEventListener`, не
делает ничего — это наследие обработчиков в атрибутах.

### Слушатель тоже вешается дважды

Модуль может выполниться второй раз — страницу вернули из кеша. Тогда
слушателей станет два, и каждое нажатие сработает дважды: мел поставится и
тут же снимется.

```js
if (!register.dataset.wired) {
  register.dataset.wired = "yes";
  register.addEventListener("click", …);
}
```

То же правило «найти или создать», что в `s03e02`, только про поведение.

### Где это в Rails

```erb
<div data-controller="register" data-action="click->register#chalk">
```

Stimulus вешает **один** слушатель на контроллер и разбирает, на чём началось,
— то есть делает ровно то, что написано выше, но объявлением в разметке.
Поэтому строка, пришедшая Turbo Stream'ом, работает сразу: контроллер её не
знает и знать не должен.

Оттуда же `data-action="submit->register#send"` — перехват отправки формы, и
`preventDefault` Stimulus делает сам, если обработчик вернул не `false`.

## Проверка: ADA задаёт вопросы

```
[ADA · КАБЕЛЬ]
ТРИ ВОПРОСА.
```

**1.** ADA: «Слушатель на каждой записи. Пришла новая запись. Что произойдёт
при нажатии на неё?»

<details><summary>Ответ</summary>

Ничего. Слушателя ей не досталось: его вешали, когда её ещё не было.

Ошибки при этом не будет — будет тишина, и чинить её начнут с того, что
нажмут ещё раз. Это главный довод за делегирование: не «короче», а «работает
на том, чего ещё нет».
</details>

**2.** ADA: «`event.target` и `event.currentTarget`. Нажали по абзацу внутри
записи, слушают на журнале. Что где?»

<details><summary>Ответ</summary>

`target` — абзац: на нём началось. `currentTarget` — журнал: на нём слушают.

Нужен обычно ни тот, ни другой, а запись между ними — её находит
`event.target.closest("li[data-id]")`. Сравнивать `target` со списком записей
нельзя: нажали-то по абзацу.
</details>

**3.** ADA: «`preventDefault` у формы подачи, но отправлять пока нечем. Что
получится?»

<details><summary>Ответ</summary>

Форма перестанет работать. Нажатие на «Передать» не сделает ничего: браузеру
запретили, а взамен не дали.

Отменять действие по умолчанию можно только тогда, когда есть чем его
заменить, — и это разбирается в следующей серии. До неё форма подачи
отправляется на сервер, как умеет.
</details>

## Разбор типичных ошибок

1. **Слушатель на каждой записи.** На той, что придёт следующей, его не будет.
2. **`event.target` сравнивают со списком.** Нажали по абзацу внутри — мимо.
3. **Список узлов взят один раз.** Дерево меняется, список нет.
4. **Отбор удаляет записи.** «Показать все» их уже не вернёт.
5. **Отбор необратим.** Спрятал и не показал обратно.
6. **Отправка формы отбора не отменена.** Enter в списке перезагрузит
   страницу.
7. **Отменена отправка формы подачи.** Запись перестала уходить вовсе.
8. **Ссылку внутри записи не пропустили.** Одно нажатие делает две вещи.
9. **`stopPropagation` «чтобы не мешало».** Линия порвана, виноватого ищут
   долго.
10. **Слушатели вешаются при каждом запуске модуля.** Нажатие срабатывает
    дважды и отменяет само себя.
