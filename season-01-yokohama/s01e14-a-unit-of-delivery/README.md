## Теория: как библиотека находит себя

### Одно имя снаружи

```ruby
require "abacus"
Abacus::Ledger.new(entries)
```

Гем занимает **ровно одно** имя верхнего уровня — своё. Всё остальное живёт
внутри модуля. Причина не в эстетике: два гема, определившие `Entry` в
глобальном пространстве, несовместимы, и узнает об этом тот, кто подключит оба.

### Точка входа

`lib/abacus.rb` — единственный файл, который подключают снаружи. Он объявляет
модуль, версию и подтягивает остальное:

```ruby
module Abacus
  VERSION = "1.0.0"
end

require "abacus/errors"
require "abacus/keys"
...
```

Правило именования жёсткое: `require "abacus"` ищет `abacus.rb` в каталогах из
`$LOAD_PATH`; RubyGems кладёт туда `lib` установленного гема. Отсюда и
раскладка `lib/имя.rb` + `lib/имя/*.rb`.

### `require` против `require_relative`

| | Ищет | Где уместно |
|---|---|---|
| `require "abacus/keys"` | по `$LOAD_PATH` | **в геме** |
| `require_relative "keys"` | рядом с текущим файлом | в приложении, в скриптах, в тестах |

`require_relative` работает при разработке, потому что файлы лежат рядом. В
установленном геме они лежат там же — но подключать их будут иначе, и любая
пересборка раскладки (например, `lib/abacus/v2/`) сломает пути. Гемы пишут на
`require`, и проверка этой серии специально раскладывает файлы так, что
`require_relative` не находит ничего.

Ещё одно отличие: `require` дедуплицирует по **разрешённому пути**, а
`require_relative` — по абсолютному. Один и тот же файл, подключённый обоими
способами, загрузится дважды: константы переопределятся, методы переопределятся,
и предупреждение об этом легко пропустить.

### Порядок подключения

```ruby
require "abacus/totals"
require "abacus/dynamic"    # dynamic.rb делает include Totals при чтении класса
```

Тело класса выполняется в момент чтения файла. Если `include Totals` встретится
раньше, чем определён `Totals`, будет `NameError` — и указывать он будет на
строку `include`, а не на порядок в точке входа.

Порядок важен только там, где один файл нужен другому **при чтении**: примеси,
наследование, константы. Для методов, которые просто вызывают чужой класс,
порядок безразличен — к моменту вызова загружено уже всё.

### `gemspec` — паспорт

```ruby
require_relative "lib/abacus"     # чтобы взять версию оттуда

Gem::Specification.new do |spec|
  spec.name = "abacus"
  spec.version = Abacus::VERSION
  spec.license = "MIT"
  spec.required_ruby_version = ">= 3.1.0"
  spec.files = Dir["lib/**/*.rb", "README.md", "LICENSE"]
  spec.require_paths = ["lib"]
end
```

Это обычный Ruby, исполняемый при сборке. Отсюда две практики:

- **версия берётся из библиотеки.** Записанная и там и тут, она разойдётся при
  первом же выпуске в спешке;
- **`Dir`, а не `git ls-files`.** Второе — распространённая заготовка, и она
  даёт пустой список везде, где нет репозитория: в архиве с исходниками, в
  контейнере сборки, в vendored-копии.

`required_ruby_version` не вежливость: без него гем установится на старый
Ruby и сломается в чужом коде синтаксической ошибкой.

### Где это в Rails

Приложение Rails — не гем, но устроено так же: `config/application.rb` —
точка входа, `Gemfile` перечисляет гемы, `bundler` складывает их `lib` в
`$LOAD_PATH`. Разница в том, что Rails подключает файлы приложения сам, по
именам классов (автозагрузка Zeitwerk), — и потому имена файлов там обязаны
соответствовать именам классов. Правило то же самое, просто применяется
автоматически.

## Проверка: ADA задаёт вопросы

```
[ADA · ЛЕНТА ИЗ ЛОНДОНА]
ТРИ ВОПРОСА.
```

**1.** ADA: «В геме `require_relative`. Всё работает. Почему это ошибка?»

<details><summary>Ответ</summary>

Потому что работает **пока**. `require_relative` привязывает файл к его соседям
по каталогу; гем же — единица, которую переносят, распаковывают в другое место
и подключают через `$LOAD_PATH`.

Второй, менее очевидный вред: файл, подключённый один раз через `require`, а
другой через `require_relative`, загрузится дважды. Классы переоткроются,
константы переопределятся, и единственным следом будет предупреждение, которое
никто не читает.
</details>

**2.** ADA: «Версия в паспорте написана числом. Что в этом плохого, если она
верная?»

<details><summary>Ответ</summary>

Она верная сегодня. Выпуск версии — это правка в одном месте, и второе место
забудут: гем соберётся под номером `1.0.0`, а `Abacus::VERSION` внутри будет
говорить `1.1.0`. Тот, кто потом станет искать, откуда взялось расхождение,
потратит день.

Одно знание — одно место. Паспорт читает библиотеку, а не наоборот.
</details>

**3.** ADA: «`spec.files = \`git ls-files\`.split` — так написано в половине
гемов. Чем плохо?»

<details><summary>Ответ</summary>

Тем, что предполагает репозиторий. Гем собирают и из архива с исходниками, и в
контейнере, куда `.git` не копируют, и из vendored-копии внутри чужого
проекта. Во всех этих случаях список файлов окажется пустым, гем соберётся
пустым, и ошибка проявится у того, кто его установит.

`Dir[...]` не зависит ни от чего, кроме файлов на диске.
</details>

## Разбор типичных ошибок

1. **`require_relative` в точке входа.** Работает при разработке, ломается в
   геме.
2. **Неверный порядок подключения.** `include` из файла, который ещё не
   прочитан, даёт `NameError` с непонятным адресом.
3. **Версия, записанная дважды.** Разойдётся.
4. **`git ls-files` в списке файлов.** Пустой гем там, где нет репозитория.
5. **Забыть `required_ruby_version`.** Гем установится на Ruby 2.7 и упадёт
   синтаксической ошибкой в чужом коде.
6. **Оставить заготовку в `summary`.** «TODO: Write a short summary» —
   надпись, с которой гемы действительно выкладывают.
7. **Определить что-то вне модуля.** Гем перестанет сочетаться с другими.
