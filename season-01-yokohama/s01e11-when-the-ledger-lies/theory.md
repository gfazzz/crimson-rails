# Теория — s01e11

## 1. Дерево исключений Ruby

```
Exception
├── NoMemoryError, SystemExit, SignalException, Interrupt, ScriptError
└── StandardError
    ├── ArgumentError, KeyError, IndexError, NameError, NoMethodError
    ├── TypeError, ZeroDivisionError, IOError, RuntimeError
    └── ← сюда вешают свои
```

Верхняя ветка — то, что не должно перехватываться прикладным кодом:
`Interrupt` (Ctrl-C), `SystemExit` (вызов `exit`), `NoMemoryError`. Поймав их,
программа перестаёт слушаться пользователя и операционную систему.

`raise "текст"` без класса создаёт `RuntimeError` — это законно для черновика
и плохо для библиотеки: поймать такую ошибку можно только вместе со всеми
остальными `RuntimeError` в процессе.

## 2. Зачем свой корень

```ruby
rescue Abacus::Error => e     # всё своё
rescue Abacus::LedgerError    # только беды ведомости
rescue Abacus::MalformedRow   # только одна
```

Иерархия позволяет ловить на нужном уровне общности, а вызывающему коду —
выбирать, насколько подробно он хочет разбираться. Без общего корня в каждом
`rescue` появляется список классов, и этот список устаревает молча.

Правило: **корень на библиотеку, ветки на способ лечения.** Ветки различают
не по месту возникновения, а по тому, что с ними делают: повторить, сообщить
пользователю, записать в журнал и продолжить.

## 3. Что положить в исключение

```ruby
class LedgerError < Error
  attr_reader :line, :row
  def initialize(message, line: nil, row: nil)
    @line = line
    @row = row
    super(build_message(message, line))
  end
end
```

Текст читает человек. Поля читает код: по `error.line` можно показать строку в
интерфейсе, по `error.row` — приложить саму запись к письму.

Осторожно с тем, что кладётся в поля: исключения попадают в журналы и в
системы сбора ошибок. Пароль, токен или персональные данные, положенные в
исключение, оказываются в трёх местах сразу.

## 4. `raise` в подробностях

```ruby
raise                                # переподнять текущую ошибку (внутри rescue)
raise "текст"                        # RuntimeError
raise MalformedRow                   # без сообщения
raise MalformedRow, "нет кода"       # класс + сообщение
raise MalformedRow.new("нет кода", line: 203)   # готовый объект
```

Форма с готовым объектом нужна, когда конструктор принимает больше, чем
сообщение, — как у нас.

Голый `raise` внутри `rescue` переподнимает **текущее** исключение, сохраняя
трассу. Это то, что пишут после исчерпания повторов.

## 5. `retry`: три правила

```ruby
attempts = 0
begin
  attempts += 1
  source.fetch
rescue TransmissionError
  retry if attempts < MAX
  raise
end
```

1. **Считай попытки.** Без счётчика — вечный цикл.
2. **Повторяй только то, что может измениться.** Разбор той же строки —
   не может.
3. **Подумай о паузе.** В реальной системе между попытками ждут, и обычно с
   возрастанием: 1 с, 2 с, 4 с. Без паузы три попытки уйдут за миллисекунду
   и лягут на ту же неработающую линию.

Четвёртое правило появляется, когда повторяется операция с побочным эффектом:
она должна быть **идемпотентной**, иначе повтор создаст второй платёж. Это
тема сезона 6, и она вырастает ровно отсюда.

## 6. `ensure` и его ловушки

```ruby
def load
  file = File.open(path)
  ...
ensure
  file&.close         # &. — файл мог не открыться вовсе
end
```

| Что написать в `ensure` | Что получится |
|---|---|
| `return значение` | исключение исчезает, наружу уходит значение |
| `raise Другое` | исходная ошибка подменена |
| код, который может упасть | то же самое, только случайно |
| освобождение ресурса | правильно |

Лучший способ не ошибиться — не писать `ensure` вручную там, где есть блочная
форма: `File.open(path) { |f| ... }` закрывает файл сам, и закрывает верно.

## 7. `cause`: цепочка причин

```ruby
begin
  registry.fetch(code)
rescue KeyError => e
  raise UnknownRoad.new("дорога #{code} не в реестре")
end
```

Новое исключение автоматически получает `cause`, указывающий на `KeyError`.
В трассе видны оба, и это правильный способ оборачивать чужие ошибки в свои:
наружу идёт понятное сообщение, внутрь — техническая правда.

Потерять причину можно, подняв исключение вне `rescue` — тогда `cause` пуст.

## 8. Где это в Rails

| Rails | Соответствие |
|---|---|
| `rescue_from` в контроллере | общий корень и ветки |
| `retry_on` / `discard_on` в Active Job | разделение «повторять / не повторять» |
| `ActiveRecord::RecordInvalid` несёт `record` | контекст в объекте ошибки |
| `find_by` против `find` | `nil` против исключения — разные договоры |

Последняя строка — отдельный разговор: не всякая неудача обязана быть
исключением. `find_by` возвращает `nil`, потому что «не нашлось» — обычный
исход. `find` бросает, потому что обращение по идентификатору предполагает,
что запись есть. Выбор между `nil` и исключением — это выбор между «бывает» и
«не должно случаться».
