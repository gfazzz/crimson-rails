## Чему ты научишься

- Перехватывать вызов метода, которого нет, — `method_missing`.
- Второй половине дела — `respond_to_missing?`, — без которой объект отвечает
  на вопрос и одновременно отрицает, что умеет.
- `super` в обе стороны: он и возвращает нормальный `NoMethodError`, и
  пропускает имя дальше по цепочке предков.
- Приёму, который дороже синтаксиса: **перехватывая всё, ты обязан вернуть
  назад то, что не твоё.** Иначе опечатка перестаёт быть ошибкой.

Подробнее — в [`theory.md`](theory.md).

## Теория: когда метода нет

### Что делает Ruby

Вызов `finder.find_by_road("SJI")` идёт по цепочке предков. Метод не найден —
и вместо немедленной ошибки Ruby посылает объекту **другой** метод:

```ruby
finder.method_missing(:find_by_road, "SJI")
```

Реализация по умолчанию (в `BasicObject`) поднимает `NoMethodError`. Всё, что
ты делаешь, — перехватываешь её на своём уровне.

```ruby
def method_missing(name, *args, &block)
  match = PATTERN.match(name.to_s)
  return super unless match          # не наше — отдай дальше

  ...
end
```

### `super` — не вежливость, а обязанность

`return super unless match` делает две вещи сразу.

**Возвращает нормальную ошибку.** Без `super` `finder.find_by_clerk("Ито")`
вернёт `nil`, и опечатка станет обычным значением. Программа продолжит
работать с пустым ответом, а ошибку найдут через неделю в отчёте.

**Пропускает имя дальше по цепочке.** В этом классе подмешан модуль `Totals`,
разбирающий свои имена — `total_by_road`. Он стоит **позади** `Finder`:

```
[Finder, Totals, Object, ...]
```

Твой `method_missing` вызывается первым. Не передашь `total_by_road` дальше —
модуль не получит ничего, и его методы просто исчезнут. Без ошибки, без следа.

### `respond_to_missing?`

```ruby
finder.respond_to?(:find_by_road)   # без respond_to_missing? — false
finder.method(:find_by_road)        # без него — NameError
```

`respond_to?` и `method` спрашивают объект через `respond_to_missing?`.
Переопределять надо **именно его**, а не `respond_to?`: `method`, `to_proc`,
`Method#owner` и половина стандартной библиотеки идут мимо `respond_to?`.

Объект, который отвечает на `find_by_road`, но говорит `respond_to?` → `false`,
врёт. Это ломает всё, что проверяет наличие метода перед вызовом, — от
сериализации до тестовых заглушек.

И здесь тот же `super`, по той же причине: имена, которые разбирает модуль
позади, должны признаваться и им.

### Цена

`method_missing` срабатывает **после** неудачного поиска по всей цепочке
предков — то есть каждый такой вызов дороже обычного. Плюс разбор имени
строкой или регулярным выражением на каждом вызове.

Для отчёта по четырёмстам записям это незаметно. Для метода, вызываемого в
цикле миллион раз, — заметно. Отсюда приём, который Rails применяет
повсеместно: **перехватить один раз, определить метод и больше не
перехватывать.** Это `define_method`, и это следующая серия.

### Чем платят за динамику

- метода не видно в `instance_methods`, `grep` по коду его не найдёт;
- подсказки редактора не работают;
- трасса при ошибке внутри становится длиннее и непонятнее;
- опечатка превращается в ошибку времени выполнения, а не чтения.

Поэтому `method_missing` уместен там, где имён действительно много и они
следуют явному образцу. Четырнадцать методов по образцу — уместен. Три
метода — нет, просто напиши три метода.

### Где это в Rails

```ruby
Entry.find_by_road_and_cargo("SJI", "чай")   # исторический find_by_*
params.dig(:entry, :road)
record.road_changed?                          # Active Model Dirty
```

Первая строка — классический `method_missing` в Active Record; современный
`find_by(road:, cargo:)` пришёл ему на смену как раз потому, что имена
перестали быть данными. Третья — семейство методов, порождаемых по именам
колонок; именно там применяется приём «определить и больше не
перехватывать».

**1.** ADA: «`method_missing` возвращает `nil` для незнакомых имён вместо
`super`. Назови, что произойдёт с опечаткой.»

<details><summary>Ответ</summary>

Опечатка перестанет быть ошибкой. `finder.find_by_clrek("Ито")` вернёт `nil`,
код продолжит работу, в отчёт попадёт пустая строка. Ошибка проявится далеко
от места, где сделана, и будет выглядеть как «неверные данные», а не как
«неверный код».

`super` возвращает `NoMethodError` с правильным именем — то есть превращает
молчаливую порчу данных в громкую ошибку.
</details>

**2.** ADA: «Почему `respond_to?` мало и нужен `respond_to_missing?`?»

<details><summary>Ответ</summary>

Потому что `respond_to?` — лишь одна из дверей. `method(:name)`,
`Method#to_proc`, `public_send` с проверкой, тестовые заглушки, сериализаторы —
все они спрашивают `respond_to_missing?` напрямую.

Переопределив `respond_to?`, получишь объект, который на словах умеет, а
`method(:find_by_road)` по-прежнему даёт `NameError`. Ровно этот случай
проверяется тестом.
</details>

**3.** ADA: «В классе подмешан модуль, который тоже разбирает имена. Что
случится, если не передать незнакомое имя через `super`?»

<details><summary>Ответ</summary>

Методы модуля исчезнут. Не сломаются, не выдадут ошибку — их просто не
станет, потому что до модуля вызов не дойдёт: он стоит в цепочке позади.

Это самый неприятный вид поломки: код модуля на месте, тесты модуля в
изоляции зелёные, а в приложении его как не бывало.
</details>

## Разбор типичных ошибок

1. **`return nil` вместо `super`.** Опечатка становится значением.
2. **Забыть `respond_to_missing?`.** `method(:find_by_road)` перестанет
   существовать.
3. **Переопределить `respond_to?`.** То же самое, но выглядит правильно.
4. **`super` не вызван в `respond_to_missing?`.** Имена подмешанного модуля
   перестанут признаваться.
5. **Не проверять число аргументов.** Обычный метод сообщает об этом сам;
   разбираемый — только если ты напишешь.
6. **Сделать `method_missing` публичным.** Он служебный: его зовёт язык, а не
   человек.
7. **Слишком широкий образец.** `\Afind_by_(.+)\z` примет `find_by_clerk` и
   вернёт пустой список вместо ошибки.
