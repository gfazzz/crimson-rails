# Теория — s01e12

## 1. Что происходит при вызове метода

1. Ruby ищет метод по цепочке предков получателя, слева направо.
2. Не нашёл — посылает получателю `method_missing(имя, *аргументы, &блок)`.
3. `BasicObject#method_missing` поднимает `NoMethodError`.

Третий шаг — обычный метод, который можно перехватить. Никакой особой машинерии
здесь нет: «метод не найден» — это просто ещё один вызов.

То же устройство у `const_missing` (для констант) и `respond_to_missing?` (для
вопроса «умеешь ли»).

## 2. Полная сигнатура

```ruby
def method_missing(name, *args, **kwargs, &block)
  return super unless handles?(name)
  ...
end
```

`name` — символ. Именованные аргументы в Ruby 3 приходят отдельно, и если
перехватчик должен их пропускать, `**kwargs` обязателен — иначе они
превратятся в позиционный хеш при пересылке.

Форма `def method_missing(name, ...)` с оператором `...` пересылает всё сразу
и годится, когда разбирать аргументы не нужно.

## 3. Три обязанности перехватчика

| Обязанность | Как |
|---|---|
| разобрать свои имена | образец, узкий и явный |
| отдать чужие дальше | `super` |
| признаться, что умеет | `respond_to_missing?` |

Пропуск любой из трёх даёт свой вид поломки:

- без разбора — ничего не работает (заметно);
- без `super` — опечатки становятся `nil`, чужие перехватчики исчезают
  (незаметно);
- без `respond_to_missing?` — объект врёт о себе (незаметно до интеграции).

## 4. `respond_to?` против `respond_to_missing?`

```ruby
obj.respond_to?(:foo)        # спрашивает язык → внутри зовёт respond_to_missing?
obj.method(:foo)             # зовёт respond_to_missing? напрямую
obj.public_send(:foo)        # не спрашивает вовсе, просто вызывает
```

Правило: **переопределяют `respond_to_missing?`, читают `respond_to?`.**

Второй аргумент `include_private` нужен, чтобы различать публичные и приватные
имена. Его почти всегда просто передают в `super`.

## 5. Цена

```
обычный вызов          ~1
method_missing         ~5–20 (поиск по всей цепочке + вызов + разбор имени)
```

Порядок величины, не измерение: точные числа зависят от версии и глубины
иерархии. Вывод практический: динамический разбор дешёв в отчёте и дорог в
цикле.

Отсюда приём «определить и забыть»:

```ruby
def method_missing(name, *args)
  return super unless handles?(name)

  self.class.define_method(name) { |value| ... }   # определили один раз
  public_send(name, *args)                          # и сразу позвали
end
```

Второй вызов уже находит настоящий метод и до `method_missing` не доходит.
Именно так устроены динамические атрибуты в Active Record. Это тема следующей
серии.

## 6. Когда не надо

`method_missing` уместен, если:

- имён много и они следуют явному образцу;
- набор имён известен только во время выполнения (колонки таблицы, поля
  документа);
- альтернатива — сотни одинаковых методов.

И неуместен, если:

- методов три;
- образец широкий («всё, что начинается на get_»);
- имена приходят от пользователя — тогда это не гибкость, а дыра.

Хорошая проверка: **можно ли перечислить то, что объект умеет?** Если нет,
объектом нельзя пользоваться, его нельзя документировать и нельзя проверить.

## 7. Чем заменяют

| Вместо | Лучше |
|---|---|
| `find_by_road_and_cargo(a, b)` | `find_by(road: a, cargo: b)` — данные аргументами, а не в имени |
| динамические `get_*` | `[]` или `dig` |
| сотни атрибутов | `define_method` в цикле по списку полей (s01e13) |
| делегирование | `Forwardable`, `def_delegators` |

Первая строка — история Rails: `find_by_*` через `method_missing` был заменён
на `find_by(hash)` именно потому, что имя метода — плохое место для данных.
Оно не поддаётся проверке, не экранируется и не читается инструментами.
