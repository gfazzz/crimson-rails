Код ты видишь впервые. В нём нет ни одной незнакомой конструкции.

`self.extended` — хук из девятой серии. `@_dependencies` — переменная
объекта-модуля, десятая. `base < self` — оператор, которым в девятой серии
выяснилось, что примесь не наследование. `class_eval` с блоком — подмена
`self`, десятая. `const_set`, `module_eval`, `super` внутри перехваченного
метода — двенадцатая и тринадцатая.

Сорок строк, и все сорок — из того, что ты делал руками последние пять недель.

Ты читаешь их дважды и на втором заходе замечаешь главное: этот код **ждёт**.
Примесь, включённая в другую примесь, не включается — она записывается в список
и ждёт настоящего класса. `append_features` возвращает `false`, и Ruby считает,
что ничего не произошло. Вещь, которая выглядит включённой и не включена.

Ты смотришь на эту строку дольше, чем следовало бы: она напоминает что-то
другое.

## Теория: что на самом деле делает `include`

### `append_features`

```ruby
base.include(SomeModule)
```

внутри устроено так:

1. Ruby зовёт `SomeModule.append_features(base)` — именно этот метод вставляет
   модуль в цепочку предков;
2. затем зовёт `SomeModule.included(base)` — хук, который ты писал в `s01e09`.

Хук `included` — уведомление: срабатывает **после** и ничего не решает.
`append_features` — сама операция, и, перехватив её, можно решить не
включаться вовсе. На этом построен весь приём: посмотреть, кто включает, и
либо включиться, либо записаться в очередь.

### Зачем ждать

Задача, которую в `s01e09` пришлось обходить руками:

```ruby
module Billable
  include Weighable          # обычный include: Weighable уходит внутрь Billable
end

class Shipment
  include Billable
end
```

С обычными модулями `Weighable::ClassMethods` **не подключится** к `Shipment`:
хук `Weighable.included` получил в `base` модуль `Billable`, а не класс, и
`base.extend(ClassMethods)` дал методы класса модулю — то есть никому.

Примесь решает это ожиданием:

```ruby
def append_features(base)
  if base.instance_variable_defined?(:@_dependencies)
    base.instance_variable_get(:@_dependencies) << self   # это примесь — ждём
    false
  else
    @_dependencies.each { |dep| base.include(dep) }       # это класс — разворачиваем
    super
    base.extend const_get(:ClassMethods) if const_defined?(:ClassMethods)
    base.class_eval(&@_included_block) if instance_variable_defined?(:@_included_block)
  end
end
```

Признак «это примесь, а не класс» — наличие `@_dependencies`, заведённой в
`self.extended`. Никакой проверки типов: объект опознаётся по тому, что у него
есть, — та же утиная типизация, что в `s01e02`.

### Порядок предков

```ruby
@_dependencies.each { |dependency| base.include(dependency) }
super
```

Сначала зависимости, потом себя. Тогда в цепочке зависящий окажется **ближе**
к классу:

```
[Shipment, Billable, Weighable, Object]
```

и сможет перекрывать методы того, от кого зависит. Обратный порядок дал бы
обратное поведение — и никто бы не заметил, пока имена методов не совпали.

### `included` в двух ролях

```ruby
included do ... end      # без аргумента: объявление отложенного блока
included(base)           # с аргументом: обычный хук Ruby
```

Один метод, два назначения, различаемые по наличию аргумента. Приём спорный —
экономит имя ценой неочевидности, — но встречается часто.

Блок выполняется через `base.class_eval`: `self` в нём — класс-хозяин
(`s01e10`), поэтому внутри работают `validates`, `attr_reader` и всё прочее,
что пишут в теле класса.

### `base < self`

```ruby
return false if base < self
```

Оператор из `s01e09`: для класса и модуля `<` означает «включает». Строка
целиком читается как «если уже включены — ничего не делать», и без неё блок
`included` выполнился бы повторно при повторном включении.

### Где это в Rails

```ruby
module Auditable
  extend ActiveSupport::Concern

  included do
    has_many :audit_entries, as: :subject
  end

  class_methods do
    def audited? = true
  end

  def audit!(action) = audit_entries.create!(action: action)
end
```

Так выглядит `app/models/concerns/*.rb` в любом приложении Rails. Прочитав
сегодняшний файл, ты знаешь про него всё, включая то, почему `included do`
пишут именно так и почему порядок `include` внутри concern-ов имеет значение.

## Проверка: ADA задаёт вопросы

```
[ADA · ЛЕНТА ИЗ ЛОНДОНА]
ТРИ ВОПРОСА. ПОСЛЕДНИЕ В ЭТОМ СЕЗОНЕ.
```

**1.** ADA: «Почему перехватывается `append_features`, а не `included`?»

<details><summary>Ответ</summary>

Потому что `included` — уведомление, приходящее **после** включения, и
отменить ничего не может. `append_features` — сама операция: вернув из него
`false`, модуль не включается вовсе.

Вся конструкция держится на возможности **не включиться**, а её даёт только
`append_features`.
</details>

**2.** ADA: «Как код отличает примесь от обычного класса?»

<details><summary>Ответ</summary>

По наличию переменной `@_dependencies`, которую заводит `self.extended` в
момент `extend Abacus::Concern`. Есть переменная — перед нами такая же примесь,
и включаться рано; нет — настоящий класс, пора разворачиваться.

Это утиная типизация из `s01e02`, применённая к модулям: спрашивают не «какого
ты класса», а «что у тебя есть».
</details>

**3.** ADA: «Зависимости включаются в `base`, а не в `self`. Почему это не то
же самое?»

<details><summary>Ответ</summary>

`base.include(dependency)` кладёт зависимость прямо в класс-хозяин, и её
`ClassMethods` достаются ему. `self.include(dependency)` положил бы её внутрь
примеси — и `ClassMethods` достались бы примеси, то есть никому.

Ровно эту ошибку курс обходил руками в `s01e09`. Здесь она исправлена в
корне — и именно поэтому такой модуль называется примесью-с-зависимостями, а
не просто модулем.
</details>

## Разбор типичных ошибок

1. **Перехватить `included` вместо `append_features`.** Отменить включение
   уже нельзя.
2. **Включать зависимости в себя, а не в класс-хозяина.** `ClassMethods`
   уедут не туда — та самая ошибка, ради которой всё написано.
3. **Забыть `super` или поставить его раньше зависимостей.** В первом случае
   методов самой примеси не будет, во втором цепочка предков выстроится задом
   наперёд.
4. **Забыть `base < self`.** Блок `included` выполнится повторно.
5. **`module_eval` вместо `base.class_eval`.** Блок выполнится в примеси:
   `self` не тот, и объявления уйдут не туда.
6. **`class_methods`, создающий новый модуль при каждом вызове.** Второй вызов
   затрёт первый.
