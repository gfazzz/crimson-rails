## Чему ты научишься

- Различать три формы обхода: **преобразование**, **отбор** и **свёртка**, — и
  выбирать нужную, а не первую попавшуюся.
- Тому, что `reduce` умеет не только складывать.
- Двум местам, где Ruby молча возвращает не то: `reduce` без начального
  значения на пустой коллекции и целочисленное деление.
- Приёму, который дороже синтаксиса: **отвечать `nil` там, где ответа нет.**
  Ноль — это ответ «было, и равно нулю»; он врёт, когда не было ничего.

Подробнее — в [`theory.md`](theory.md).

## Теория: три формы одного обхода

### Преобразование: `map`

Каждый элемент превращается в другой. На выходе столько же элементов, сколько
было.

```ruby
ledger.map { |entry| entry[:charge] }   # 412 записей → 412 чисел
```

`map` не фильтрует и не считает. Если после `map` хочется написать `.compact` —
значит, нужен был не `map`, а `filter_map`:

```ruby
ledger.map { |e| e[:charge] if e[:cargo] == "чай" }.compact   # два обхода и мусор
ledger.filter_map { |e| e[:charge] if e[:cargo] == "чай" }    # один
```

### Отбор: `select`, `reject`, `partition`

Элемент остаётся или уходит; сам он не меняется.

```ruby
ledger.select { |e| e[:weight] > 2000 }   # тяжёлые
ledger.reject { |e| e[:weight] > 2000 }   # лёгкие
```

`reject` — не украшение. `select { |e| !(e[:weight] > 2000) }` читается хуже
ровно на одно отрицание, а отрицания — то место, где ошибаются.

Когда нужны обе половины, `select` и `reject` подряд — это два обхода одного и
того же условия:

```ruby
heavy, light = ledger.partition { |e| e[:weight] > 2000 }
```

`partition` всегда возвращает **два** массива, даже если один из них пуст.

### Свёртка: `reduce`

Много элементов сходятся в одно значение. Блок получает накопитель и очередной
элемент и возвращает новый накопитель.

```ruby
ledger.reduce(0) { |sum, entry| sum + entry[:charge] }
```

Начальное значение — не формальность:

```ruby
[].reduce { |a, b| a + b }      # nil
[].reduce(0) { |a, b| a + b }   # 0
```

Без него `reduce` берёт первый элемент как начальный, а на пустой коллекции
первого элемента нет. `nil` уедет в вызывающий код и всплывёт через две функции
сообщением `undefined method '+' for nil`.

**`reduce` — не только сумма.** Накопителем может быть что угодно:

```ruby
ledger.reduce(nil) do |longest, entry|
  name = entry[:cargo]
  longest.nil? || name.length > longest.length ? name : longest
end
```

Сравнение здесь строгое (`>`, не `>=`) — и это видимое решение: при равной
длине остаётся тот, кто встретился раньше. Нестрогое сравнение оставило бы
последнего. Оба варианта допустимы, но выбирать надо осознанно, а не как
получится.

### `sum` — частный случай, а не замена

`ledger.sum { |e| e[:charge] }` короче и быстрее (внутри он умеет
компенсировать погрешность при сложении дробей). Писать `reduce` там, где
хватает `sum`, незачем. Но `reduce` нужно уметь читать: на нём написана
половина чужого кода, включая внутренности `Enumerable`.

### Где ноль врёт

```ruby
def average_charge
  count = @ledger.count
  return nil if count.zero?

  total_charge.to_f / count
end
```

Две ловушки в трёх строках:

- **`nil`, а не `0`.** «Средняя плата равна нулю» означает, что перевозки были и
  все бесплатные. Когда перевозок не было, правильный ответ — «средней нет».
- **`.to_f`.** `3 / 2` в Ruby равно `1`. Целочисленное деление не ошибка и не
  предупреждение — просто другой ответ, и его никто не заметит, пока разница не
  накопится.

### Где это в Rails

```ruby
Entry.where(road: "SJI").sum(:charge)      # SQL SUM — считает база
Entry.where(road: "SJI").sum(&:charge)     # Enumerable — вытащит всё в память
entries.partition(&:heavy?)
```

Первые две строки выглядят почти одинаково и делают разное. Разница — та же,
что между `order` и `sort_by` из прошлой серии: где происходит работа.

**1.** ADA: «`ledger.reduce { |sum, e| sum + e[:charge] }` — ведомость пустая.
Что вернётся и почему это опаснее исключения?»

<details><summary>Ответ</summary>

Вернётся `nil`. Опаснее исключения потому, что программа не остановится: `nil`
уедет в вызывающий код, попадёт в отчёт, будет сложен с другим числом через две
функции — и сломается там, где ошибки нет. Исключение указывает на место
ошибки, `nil` указывает на место, куда он успел доехать.

Лечится начальным значением: `reduce(0)`.
</details>

**2.** ADA: «Тебе нужны и тяжёлые, и лёгкие. Чем плохо написать `select`, а
потом `reject`?»

<details><summary>Ответ</summary>

Два обхода вместо одного — но это не главное. Главное, что условие записано
дважды, и когда завтра порог «тяжести» изменится с двух тонн на полторы,
поправить нужно будет в двух местах. Одно из них забудут.

`partition` записывает условие один раз и возвращает обе половины.
</details>

**3.** ADA: «`total_charge / count` вместо `total_charge.to_f / count`. Когда
эта ошибка проявится?»

<details><summary>Ответ</summary>

Никогда — в смысле «никогда не упадёт». Целочисленное деление в Ruby законно и
молча отбрасывает дробную часть: средняя плата 1,5 станет 1. Отчёт будет
выглядеть правдоподобно и врать примерно на треть процента, что как раз столько,
чтобы не заметить и достаточно, чтобы не сойтись при сверке.

Такие ошибки ловятся не чтением кода, а проверкой на данных, где ответ заведомо
дробный. В тесте она есть.
</details>

## Разбор типичных ошибок

1. **`reduce` без начального значения.** На пустой ведомости вернётся `nil`.
2. **`select` + `reject` вместо `partition`.** Условие в двух местах.
3. **`sort` в `roads`.** Спросили «какие дороги встречались», а не «какие есть
   вообще»: порядок появления — часть ответа.
4. **Нестрогое сравнение в `longest_cargo_name`.** При равной длине останется
   последний вместо первого. Тест это фиксирует как договор.
5. **Целочисленное деление в средней.** Молча, без предупреждения, примерно
   верно.
6. **Дописать всё это в `Ledger`.** Класс, который и хранит, и отвечает, через
   месяц не объяснить новичку. Ведомость ведут, отчёт составляют.
