## Чему ты научишься

- Чем символ отличается от строки и почему `"road"` и `:road` — разные ключи.
- Приводить ключи рекурсивно, не трогая значения и не портя исходные данные.
- Искать дубликаты по **нормализованному** виду, сохраняя исходный.
- Приёму, который дороже синтаксиса: **приводи к одному виду для сравнения,
  храни в том виде, в каком получил.** Переписанные данные больше не свидетели.

Подробнее — в [`theory.md`](theory.md).

## Теория: имя и текст

### Символ — это имя, а не текст

```ruby
"road".object_id == "road".object_id   # false: две разные строки
:road.object_id  == :road.object_id    # true:  один и тот же символ
```

Строка — контейнер с текстом; каждый литерал создаёт новый объект. Символ —
**имя**: один и тот же символ во всей программе представлен одним объектом, он
заморожен и сравнивается мгновенно, потому что сравнивать нужно не содержимое,
а тождество.

Отсюда правило, по которому их выбирают: **символ — когда значение суть имя**
(ключ, имя метода, состояние, роль); **строка — когда значение суть текст**
(груз, название дороги, сообщение пользователю).

```ruby
{ road: "SJI" }    # ключ — имя, значение — текст
```

### Почему хеш их не путает

Хеш ищет ключ по паре `hash` + `eql?`. У строки и символа они разные, и это
не оплошность, а обязательство: если бы `"road"` и `:road` считались одним
ключом, то хеш, где нужны оба — а такое бывает, — стал бы невозможен.

```ruby
{ "road" => 1, road: 2 }     # совершенно законный хеш с двумя ключами
```

Поэтому `uniq` не находит наш дубликат: он сравнивает хеши целиком, а хеши
действительно разные.

### Откуда берутся строки

В коде на Ruby ключи почти всегда символы. Строками они приходят **снаружи**:

| Источник | Ключи |
|---|---|
| литерал в коде | символы |
| `JSON.parse(text)` | строки |
| `params` в Rails | строки (обёрнутые) |
| YAML, CSV, файл настроек | строки |
| база данных | строки |

Граница между «своим» и «чужим» — ровно там, где меняется вид ключа. Это
удобно: по виду ключа видно, откуда данные.

### Приводить — да. Переписывать — нет

```ruby
def self.dedupe(rows)
  seen = []
  rows.each_with_object([]) do |row, kept|
    normalized = symbolize(row)
    next if seen.include?(normalized)

    seen << normalized
    kept << row          # кладём ИСХОДНУЮ запись, не приведённую
  end
end
```

Приведение нужно для **сравнения**. В результат кладётся то, что пришло: если
завтра выяснится, что японская контора шлёт не всё, нужно будет показать её
запись в том виде, в каком она пришла, а не в том, в какой ты её переписал.

Общее правило работы со свидетельствами: нормализованная копия — для анализа,
оригинал — для хранения. Переписанные данные перестают быть доказательством.

### `to_sym` на чужом вводе

Старое предостережение «не вызывай `to_sym` на пользовательском вводе»
происходит из времён, когда символы не собирались сборщиком мусора: можно было
исчерпать память, посылая всё новые имена. С Ruby 2.2 динамически созданные
символы собираются, и эта конкретная опасность ушла.

Осталась другая, менее эффектная: приведение чужих ключей к символам
**молчаливо принимает всё, что прислали**. Rails поэтому и держит параметры
строками, а разрешает их явным списком — `params.permit(:road, :cargo)`. Тот же
ход, что в прошлой серии с неизвестными правилами тарифа: строго то, что
понимаешь.

### `HashWithIndifferentAccess`

Rails предлагает хеш, в котором `h[:road]` и `h["road"]` — одно и то же:

```ruby
params[:road]     # работает
params["road"]    # тоже работает
```

Удобно и ровно поэтому опасно: привыкнув к нему, легко забыть, что обычный
`Hash` так не умеет, и написать `config[:base_rate]` для хеша, разобранного из
YAML. Ответом будет `nil` — без ошибки, без предупреждения.

**1.** ADA: «`uniq` не нашёл дубликат. Это ошибка `uniq`?»

<details><summary>Ответ</summary>

Нет. `uniq` сравнивает элементы через `hash` и `eql?`, и два хеша с разными
ключами действительно не равны. Ошибка не в методе, а в допущении: мы считали
одинаковым то, что язык одинаковым не считает.

Правильный ход — не чинить `uniq`, а сравнивать приведённые копии:
`rows.uniq { |row| symbolize(row) }` сделал бы то же, что наш `dedupe`, — но
оставил бы в результате исходные записи только потому, что `uniq` с блоком
возвращает элементы, а не ключи. Это стоит знать.
</details>

**2.** ADA: «Почему `symbolize` не должен трогать значения?»

<details><summary>Ответ</summary>

Потому что значение — это данные, а ключ — это имя поля. Груз «чай» обязан
остаться строкой: он текст, а не имя. Приведи значения — и `"чай"` станет
`:чай`, сравнение с ведомостью из другого источника сломается, а вывод в отчёт
станет выглядеть странно.

Правило приведения: меняем форму описания, не меняем содержание.
</details>

**3.** ADA: «В хеше есть ключ `1` — номер строки ведомости. Что с ним делать
при приведении?»

<details><summary>Ответ</summary>

Оставить числом. `1.to_sym` не существует, и попытка «привести на всякий
случай» через `to_s.to_sym` даст символ `:"1"` — ключ, которого в исходных
данных не было и по которому никто ничего не найдёт.

Приведение обязано быть **обратимым и предсказуемым**: то, что не является
строкой-именем, остаётся как есть.
</details>

## Разбор типичных ошибок

1. **Приведение на один уровень.** Вложенный хеш правил тарифа останется со
   строковыми ключами, и `tariff[:base_rate]` вернёт `nil`.
2. **`key.to_s.to_sym` для всех ключей.** Числовой ключ превратится в `:"1"`.
3. **Менять исходный хеш.** Данные, пришедшие из конторы, перестанут быть тем,
   что пришло из конторы.
4. **Класть в результат `dedupe` приведённую запись.** Тот же случай: свидетель
   переписан.
5. **Оставлять последнюю запись вместо первой.** Порядок поступления — тоже
   сведения: первой пришла та, что пришла первой.
6. **Приводить значения заодно с ключами.** Груз станет именем, отчёт —
   странным.
