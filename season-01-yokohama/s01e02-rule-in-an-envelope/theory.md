# Теория — s01e02

## 1. Три способа держать действие

| Способ | Когда исполняется | Чем платишь |
|---|---|---|
| `yield` | сейчас, внутри метода | ничем; объекта не создаётся |
| `&block` в сигнатуре | когда захочешь | один объект `Proc` на вызов метода |
| `lambda` / `proc` в переменной | когда захочешь | то же, но создаёшь сам и явно |

Первая строка — прошлая серия, вторая и третья — эта. Правило простое: пока
действие нужно только внутри метода, `yield`; как только оно должно пережить
вызов, у него должно появиться имя.

## 2. `&` — это вызов `to_proc`

Оператор `&` в списке аргументов не делает ничего волшебного: он берёт объект и
зовёт у него `to_proc`.

```ruby
class Tariff
  def initialize(rate) = @rate = rate
  def call(entry)      = entry[:charge] * @rate
  def to_proc          = method(:call).to_proc   # вот теперь & заработает
end

ledger.total_by(&Tariff.new(0.15))
```

Без `to_proc` тот же объект даст `TypeError: wrong argument type Tariff
(expected Proc)` — при том что `call` у него есть. Метод `call` нужен, чтобы
объект можно было **вызвать**; метод `to_proc` — чтобы его можно было
**передать блоком**. Это разные умения.

`Symbol#to_proc` реализован в ядре и делает ровно то, что можно написать руками:

```ruby
class Symbol
  def to_proc = ->(obj, *args) { obj.public_send(self, *args) }
end

%w[ntk sji].map(&:upcase)     # ["NTK", "SJI"]
[1, 2, 3].inject(&:+)         # 6
```

## 3. `proc` против `lambda`: два отличия, оба кусаются

**Арность.**

```ruby
p = proc   { |a, b| [a, b] }
l = lambda { |a, b| [a, b] }

p.call(1)          # [1, nil]   — прощает
l.call(1)          # ArgumentError (given 1, expected 2)
```

**`return`.**

```ruby
def report
  rule = proc { return :from_proc }
  rule.call
  :never_reached          # сюда не дойдём: return вышел из report
end

def report_l
  rule = lambda { return :from_lambda }
  rule.call
  :reached                # лямбда вернулась в себя, метод продолжился
end
```

Блок, принятый через `&block`, — всегда `proc`. Если ты раздаёшь правила
наружу и хочешь, чтобы чужой неверный вызов ломался сразу, — храни лямбды и
проверяй `rule.lambda?`.

Мнемоника: **лямбда ведёт себя как метод, `proc` — как кусок кода, вставленный
на место.**

## 4. Замыкание: переменная, а не значение

```ruby
rules = []
[1, 2, 3].each { |n| rules << -> { n } }
rules.map(&:call)          # [1, 2, 3] — у каждого блока свой n
```

Здесь всё хорошо: параметр блока `n` — новая переменная на каждую итерацию.
А вот так — нет:

```ruby
rules = []
n = 0
3.times { n += 1; rules << -> { n } }
rules.map(&:call)          # [3, 3, 3] — переменная одна на всех
```

Классическая ловушка, одинаковая в Ruby, JavaScript и Python. Лечится тем, что
переменную делают параметром: `->(value) { value }.curry[n]` или просто
`rules << ->(v = n) { v }`.

В задании это свойство работает на тебя: правило надбавки замыкает `surcharge`,
и когда приходит вторая бумага, ничего пересоздавать не нужно.

**Цена.** Пока жив `Proc`, живо и всё, что он замкнул. Правило, замкнувшее
ведомость на четыреста тысяч строк и сохранённое в долгоживущем реестре,
удержит эту ведомость в памяти навсегда. В сезоне 6 это станет отдельным
разговором про фоновые задачи: им передают идентификатор, а не объект, —
в том числе поэтому.

## 5. `Method` — третий вызываемый объект

```ruby
def surcharge_for(entry) = entry[:charge] * 0.15

m = method(:surcharge_for)   # объект Method
m.call(entry)
m.arity                      # 1
ledger.total_by(&m)          # работает: у Method есть to_proc
```

Пригодится, когда правило уже написано методом и оборачивать его в лямбду
незачем. Утиная проверка `respond_to?(:call)` пропускает и его — а проверка
`is_a?(Proc)` отвергла бы.

## 6. Карринг

```ruby
surcharge = ->(rate, entry) { entry[:charge] * rate }
tea = surcharge.curry[0.15]        # правило с одним оставшимся аргументом
ledger.total_by(&tea)
```

`curry` превращает лямбду двух аргументов в лямбду, которую можно кормить по
одному. Способ изготовить семейство правил из одного, не плодя блоков.

## 7. Где это в Rails

| Rails | Что на самом деле |
|---|---|
| `scope :recent, -> { where(...) }` | лямбда, сохранённая в классе и вызванная при обращении к scope |
| `validates :x, if: -> { ... }` | лямбда, вызываемая в контексте записи |
| `before_action :check` | символ, который превратят в вызов метода |
| `has_many :entries, -> { order(:at) }` | лямбда, применяемая к построителю запроса |

Все четыре — «действие в конверте». Фреймворк кладёт его в ящик при загрузке
класса и достаёт при обработке запроса, ровно как ты сегодня.
