# Теория — s01e03

## 1. Модуль — не класс

Модуль нельзя создать (`Enumerable.new` — ошибка) и от него нельзя наследовать.
Модуль — это **набор методов и констант, который подмешивают**. У класса один
родитель, а модулей можно подмешать сколько угодно: так Ruby обходится без
множественного наследования, не заводя его.

```ruby
Abacus::Ledger.ancestors
# [Abacus::Ledger, Enumerable, Object, Kernel, BasicObject]
```

Поиск метода идёт слева направо. Метод, определённый в самом классе,
перекрывает метод модуля — поэтому твой `total_by` побеждает, даже если бы в
`Enumerable` был метод с таким именем.

## 2. Что именно даёт `Enumerable`

Около сорока методов, и почти все сводятся к четырём образцам:

| Образец | Методы | Что делает |
|---|---|---|
| преобразование | `map`, `flat_map`, `zip` | каждый элемент → новый элемент |
| отбор | `select`, `reject`, `find`, `partition`, `group_by` | решает про каждый элемент |
| свёртка | `reduce`, `sum`, `count`, `min_by`, `max_by`, `tally` | много элементов → одно значение |
| нарезка | `each_slice`, `each_cons`, `chunk_while`, `take`, `drop` | последовательность → куски |

Знать их наизусть не нужно — нужно знать, что они есть, и заглядывать в
`ri Enumerable` прежде, чем писать цикл.

Отдельно стоит `each_entry` — да, такой метод есть и в самом `Enumerable`, и он
делает не то, что наш: обходит, разворачивая множественные значения. Наш
псевдоним его перекрывает, потому что метод класса ближе в цепочке. Случайное
совпадение имён — хороший повод помнить, как устроен поиск.

## 3. Почему `each` обязан отдавать по одному

`Enumerable` устроен как машина, которая тянет элементы. Самый наглядный
случай — `lazy`:

```ruby
(1..Float::INFINITY).lazy.map { |n| n * 2 }.first(3)   # [2, 4, 6]
```

Бесконечная последовательность обрабатывается, потому что никто не пытается
получить её целиком. То же и с твоей ведомостью: если `each` честно отдаёт
записи по одной, ленивый обход остановится, набрав нужное; если внутри `each`
собирается массив — обход отработает целиком, а ответ получится верный. Верный
ответ, полученный неправильно, — самый дорогой вид ошибки: он не проявляется,
пока данные малы.

## 4. `Enumerator` — обход, отложенный на потом

```ruby
e = ledger.each          # Enumerator
e.next                   # первая запись
ledger.each.with_index { |entry, i| ... }
ledger.each_slice(8)     # Enumerator, а не массив
```

`Enumerator` хранит получателя и имя метода; обход начинается по требованию. Без
`enum_for` в `each` половина сцеплений перестаёт работать — а сцепление и есть
то, ради чего подключают модуль.

Внутри `Enumerator` — `Fiber`, то есть настоящая приостановка исполнения.
Знать это для курса не нужно; нужно знать, что за `e.next` стоит не индекс, а
остановленный обход, и потому его нельзя «перемотать назад» без `rewind`.

## 5. Цена

`Enumerable` работает через `each`, то есть **каждый** метод — это полный обход.
Отсюда практические следствия:

```ruby
ledger.select { ... }.map { ... }      # два обхода и два массива
ledger.lazy.select { ... }.map { ... }.first(5)   # один обход, без промежуточного массива
ledger.sort_by { ... }.first(4)        # полная сортировка ради четырёх
ledger.max_by(4) { ... }               # один проход
```

На четырёхстах записях разницы нет. Правило всё равно стоит держать в голове:
там, где ответ можно получить за один проход, полная сортировка — лишняя
работа. В сезоне 4 это перестанет быть теорией: `Entry.all.sort_by(&:charge)`
вытащит из базы всё, `Entry.order(:charge)` — попросит отсортировать базу.

## 6. `Comparable` — тот же приём

```ruby
class Money
  include Comparable
  attr_reader :sen
  def initialize(sen) = @sen = sen
  def <=>(other) = sen <=> other.sen
end

Money.new(40) < Money.new(50)        # true
Money.new(40).between?(Money.new(0), Money.new(100))   # true
Money.new(40).clamp(Money.new(50), Money.new(90))      # Money(50)
```

Один метод `<=>` — и приходят шесть. Тот же контракт, что у `Enumerable`, на
другом масштабе. Пригодится в `s01e08`, когда у записи появится класс, и в
`s01e09`, где такой модуль напишешь ты.

## 7. Граница модуля: почему `select` отдаёт массив

`Enumerable` универсален, а значит ничего не знает про конструктор. Классы,
которым важно возвращать себя, решают это сами:

```ruby
# так делает ActiveRecord::Relation — упрощённо
def where(conditions)
  self.class.new(@model, @conditions.merge(conditions))
end
```

То есть цепочка `where(...).where(...)` — это не `Enumerable`, а собственный
метод, который умеет построить следующее звено. `Enumerable` там подключён для
`each`, `map`, `find_each` и прочего, что уже материализует записи.

Практическое следствие, с которым живут все: **в Rails важно, где заканчивается
цепочка запроса и начинается обход коллекции.** Всё, что после `select { }` или
`map`, происходит в памяти приложения.
