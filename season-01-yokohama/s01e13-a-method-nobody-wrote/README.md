## Теория: методы, созданные из данных

### `define_method`

```ruby
define_method(:base_rate) do
  @attributes.fetch(:base_rate) { 0 }
end
```

Метод создаётся в момент выполнения этой строки — то есть при чтении класса.
Дальше он ничем не отличается от написанного руками: виден в
`instance_methods`, находится через `method`, участвует в `respond_to?`, не
стоит ничего при вызове.

Сравнение с прошлой серией:

| | `method_missing` (s01e12) | `define_method` (сегодня) |
|---|---|---|
| когда решается | при каждом вызове | один раз, при чтении класса |
| виден в `instance_methods` | нет | да |
| цена вызова | выше обычного | обычная |
| когда применим | имена известны только в момент вызова | имена известны заранее |

Двадцать два поля тарифа известны заранее. Значит — `define_method`.

### Почему блок, а не `def`

```ruby
def field(name, default: nil)
  define_method(name) { @attributes.fetch(name) { default } }   # видит name и default
end
```

Блок — замыкание (s01e02): он помнит переменные того места, где создан. Каждый
вызов `field` создаёт свой блок со своими `name` и `default`.

С `def` так не выйдет: тело метода, объявленного через `def`, **не видит**
локальных переменных места объявления — `def` открывает новую область
видимости. Это и есть главная причина, по которой существует `define_method`.

Проверить легко: если все поля вдруг получили одно и то же умолчание, блок
замкнул общую переменную вместо своей.

### Макрос уровня класса

```ruby
class TariffRow
  extend Abacus::Macros     # field становится методом класса

  field :base_rate, default: 0
  field :minimum,   default: 0
end
```

`field` — обычный метод, вызываемый в теле класса, где `self` — сам класс
(s01e10). Никакого особого синтаксиса: `has_many`, `validates`, `scope`,
`belongs_to` устроены ровно так же.

Поэтому `extend`, а не `include`: нужен метод **класса** (s01e09). А чтобы
экземпляры получили `initialize`, `[]` и `to_h`, модуль в хуке `extended`
подмешивает себе в помощь второй модуль:

```ruby
def self.extended(base)
  base.include(InstanceMethods)
end
```

Пара «методы класса через `extend`, методы экземпляра через `include`» — самая
частая конструкция в библиотеках Ruby.

### Наследование состояния класса

```ruby
def inherited(subclass)
  super
  subclass.instance_variable_set(:@fields, fields.dup)
end
```

`@fields` принадлежит классу (s01e10) и **не наследуется**: у наследника её
просто нет, и `fields` вернёт пустой список. Значит, список надо передать
явно — и обязательно копией.

Без `dup` родитель и наследник делят один массив: поле, объявленное в
наследнике, появится у родителя. Ошибка вылезет в другом файле и через месяц.

`super` в `inherited` обязателен: хук может быть определён и выше по цепочке.

### `send` и `public_send`

```ruby
row.public_send(:base_rate)    # только публичные
row.send(:base_rate)           # любые, включая приватные
```

`send` игнорирует видимость — он для метапрограммирования и тестов. В коде,
который обращается к полю по имени, приходящему извне, нужен `public_send`:
иначе строка `"secret"`, попавшая в параметры, вызовет приватный метод.

### Где это в Rails

```ruby
class Entry < ApplicationRecord
  belongs_to :road
  validates :charge, numericality: true
end
```

`belongs_to` и `validates` — методы класса, вызванные в теле класса; они
создают методы через `define_method` и складывают объявленное в переменные
класса. `entry.road_changed?`, `entry.charge_before_last_save` — методы,
порождённые по списку колонок таблицы.

**1.** ADA: «Почему `define_method` с блоком, а не `def` внутри цикла?»

<details><summary>Ответ</summary>

`def` открывает новую область видимости: тело метода не видит локальных
переменных места объявления. Внутри `def` не будет ни `name`, ни `default` —
только константы и то, что можно получить через `self`.

Блок `define_method` — замыкание, и потому помнит и то и другое. Это
единственная причина, по которой метод вообще существует.
</details>

**2.** ADA: «Чем это лучше `method_missing` из прошлой серии?»

<details><summary>Ответ</summary>

Тем, что методы **настоящие**. Их видно в `instance_methods`, их находит
`method`, их подтверждает `respond_to?` без дополнительных усилий, они стоят
столько же, сколько обычные, и они отображаются в трассе при ошибке.

`method_missing` остаётся для случая, когда имена неизвестны заранее. Двадцать
два поля тарифа известны — значит, применять его незачем.
</details>

**3.** ADA: «`inherited` копирует список полей. Что будет без `dup`?»

<details><summary>Ответ</summary>

Родитель и наследник будут делить один массив. Поле, объявленное у наследника,
появится у родителя и у всех остальных наследников.

Проявится это не там, где написано: родительский класс начнёт требовать поле,
о котором ничего не знает, и след поведёт в файл наследника, который в этот
момент никто не подозревает.
</details>

## Разбор типичных ошибок

1. **`def` вместо `define_method`.** Тело не увидит ни имени, ни умолчания.
2. **Общая переменная вместо замыкания.** Все поля получат одно умолчание.
3. **Забыть `inherited`.** Наследник потеряет поля родителя.
4. **`inherited` без `dup`.** Наследник начнёт дописывать поля родителю.
5. **`inherited` без `super`.** Хуки выше по цепочке не сработают.
6. **`[]`, читающий `@attributes` напрямую.** Умолчание не применится.
7. **`send` вместо `public_send` в `[]`.** Имя, пришедшее извне, доберётся до
   приватных методов.
8. **Предикат через `!value.nil?`.** Поле со значением `false` окажется
   «заполненным».

читается целиком с экрана.
