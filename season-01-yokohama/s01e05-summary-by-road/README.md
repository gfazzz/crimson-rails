## Чему ты научишься

- Сворачивать коллекцию **в хеш**: `group_by`, `transform_values`, `tally`.
- `each_with_object` — когда накопитель нужно пронести через единственный
  обход, а не собирать его трижды.
- Сверять две таблицы так, чтобы не потерять строку, которой нет у одной из
  сторон.
- Приёму, который дороже синтаксиса: **сверка идёт по объединению ключей.**
  Строка, отсутствующая у тебя, — не «нет расхождения», а самое интересное
  расхождение.

Подробнее — в [`theory.md`](theory.md).

## Теория: свёртка в хеш

### `group_by` — ключ и список

```ruby
ledger.group_by { |entry| entry[:road] }
# { "NTK" => [запись, запись, ...], "KSN" => [...] }
```

Ключи — в порядке первого появления, записи внутри группы — в порядке
ведомости. Ничего не фильтруется: дорога с единственной перевозкой — такая же
дорога. Чтобы получить не списки, а числа, группы сворачивают:

```ruby
ledger.group_by { |e| e[:road] }
      .transform_values { |rows| rows.sum { |e| e[:charge] } }
# { "NTK" => 18_420, "KSN" => 14_905, ... }
```

`transform_values` меняет значения, не трогая ключи. Парный `transform_keys`
пригодится в `s01e07`, когда ключи придут строками вместо символов.

### `tally` — частый частный случай

```ruby
ledger.map { |e| e[:cargo] }.tally
# { "уголь" => 12, "рис" => 9, "чай" => 7 }
```

То же, что группировка с подсчётом размеров, только короче и за один проход.

### `each_with_object` — накопитель через один обход

Три итога по дороге можно получить тремя группировками — и это будет три
обхода ведомости и три временных хеша со списками. Или одним:

```ruby
ledger.each_with_object({}) do |entry, acc|
  row = acc[entry[:road]] ||= { count: 0, weight: 0, charge: 0 }
  row[:count]  += 1
  row[:weight] += entry[:weight]
  row[:charge] += entry[:charge]
end
```

**Порядок аргументов обратный к `reduce`** — это главная ловушка метода:

```ruby
reduce(0)            { |acc, entry| ... }   # накопитель первым
each_with_object({}) { |entry, acc| ... }   # элемент первым
```

Ошибиться легко, заметить трудно: с хешем оба варианта могут не упасть, а молча
дать чепуху.

**Чем они отличаются по сути.** `reduce` делает новым накопителем то, что
вернул блок; `each_with_object` возвращает **тот же** объект, игнорируя
значение блока. Поэтому для изменяемого накопителя берут второй:

```ruby
ledger.reduce({}) { |acc, e| acc[e[:road]] = e[:charge] }   # вернёт число, а не хеш!
```

Присваивание возвращает присвоенное значение, и оно станет накопителем на
следующем шаге. `each_with_object` от этой ошибки избавляет.

### `||=` на ключе хеша

```ruby
row = acc[entry[:road]] ||= { count: 0, weight: 0, charge: 0 }
```

«Возьми, а если там ничего нет — положи и возьми». Переменная `row` дальше
указывает на тот же хеш внутри накопителя, менять его можно прямо. Осторожно:
`||=` срабатывает и на `false`, поэтому для значений, которые бывают ложными,
нужен `fetch` с блоком.

### Сверка по объединению ключей

```ruby
(ours.keys | reported.keys).each_with_object({}) do |road, acc|
  difference = ours.fetch(road, 0) - reported.fetch(road, 0)
  acc[road] = difference unless difference.zero?
end
```

Три решения, каждое легко принять неправильно:

- **объединение (`|`), а не свои ключи.** Дорога, приславшая итог, которой нет
  у нас, — не «сошлось», а расхождение на всю сумму;
- **`fetch(road, 0)`, а не `[road]`.** Отсутствующий ключ даст `nil`, а `nil`
  нельзя вычитать. Ноль здесь честно значит «у этой стороны ничего нет»;
- **нули не попадают в ответ.** Пустой результат должен означать «всё сошлось».
  Сверку делают, чтобы не искать ненулевую строку глазами.

### Где это в Rails

`Entry.group(:road).sum(:charge)` возвращает такой же хеш прямо из базы одним
запросом; `Entry.all.group_by(&:road)` делает то, что ты пишешь сегодня, но
предварительно вытащив всё в память. На ста тысячах записей разница перестаёт
быть академической.

## Проверка: ADA задаёт вопросы

```

ТРИ ВОПРОСА.
```

**1.** ADA: «`reduce({}) { |acc, e| acc[e[:road]] = e[:charge] }` — что вернёт
этот код?»

<details><summary>Ответ</summary>

Число, а не хеш. Присваивание возвращает присвоенное значение, оно становится
накопителем на следующем шаге, и вторая итерация попытается сделать
`число[ключ] = ...`. Упадёт или, что хуже, не упадёт — если в накопителе
окажется строка. `each_with_object({})` этого не допускает: он возвращает тот
самый объект независимо от того, что вернул блок.
</details>

**2.** ADA: «Сверка идёт только по твоим дорогам. Что произойдёт, если SJI
пришлёт итог по дороге, которой нет в твоей ведомости?»

<details><summary>Ответ</summary>

Ничего не произойдёт — и это худший исход: расхождение на всю присланную сумму
не попадёт в отчёт, потому что цикл шёл по нашим ключам.

Сверка — операция про **обе** стороны. То, чего нет у одной из них, считается
нулём у неё, а не исключается. Ито вспоминал, что в декабре была пятая
дорога, — ровно тот случай.
</details>

**3.** ADA: «Почему пустой результат сверки — хороший, и почему тогда нельзя
возвращать нули?»

<details><summary>Ответ</summary>

Сверка нужна не для того, чтобы показать итоги — они уже есть в своде, — а
чтобы показать **только** требующее внимания. Пустой хеш читается мгновенно и
однозначно: всё сошлось. Вернув все дороги с нулями, заставишь читателя снова
просматривать таблицу глазами — то есть делать работу, которую сверка должна
была снять.
</details>

## Разбор типичных ошибок

1. **Три группировки вместо одного обхода.** Ответ верный, работа тройная.
   Тест считает обходы.
2. **Перепутать порядок аргументов** в `each_with_object`: он обратный к
   `reduce`.
3. **`reduce({})` с присваиванием в блоке.** Накопителем станет присвоенное
   значение.
4. **Сверять по своим ключам.** Пропущенная дорога исчезнет молча.
5. **`ours[road]` вместо `ours.fetch(road, 0)`.** `nil` нельзя вычитать, и
   сообщение об ошибке укажет не туда.
6. **Вернуть нули или взять `.abs`.** В первом случае сверка перестаёт
   отвечать на свой единственный вопрос, во втором теряется знак — а знак
   говорит, чей итог больше.
