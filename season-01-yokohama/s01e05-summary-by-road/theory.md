# Теория — s01e05

## 1. Четыре способа свернуть коллекцию в хеш

| Метод | Что даёт | Когда |
|---|---|---|
| `group_by { }` | ключ → **список** элементов | нужны сами записи группы |
| `tally` | элемент → **сколько раз** встретился | нужен только счёт |
| `partition { }` | два списка | признак двоичный |
| `each_with_object({})` | что угодно | накопитель сложнее числа |

Плюс `reduce` — тот же `each_with_object`, только накопитель приходится
возвращать самому.

## 2. `group_by` + `transform_values` — самая частая пара

```ruby
entries.group_by { |e| e[:road] }
       .transform_values { |rows| rows.sum { |e| e[:charge] } }
```

Работает в два прохода и создаёт промежуточный хеш со списками. Для четырёхсот
записей это ничего не стоит; для четырёхсот тысяч — уже стоит, и тогда пишут
`each_with_object`.

Полезные соседи: `transform_keys` (`s01e07`), `filter_map`, `sum` по хешу
(`hash.sum { |_k, v| v }`), `min_by`/`max_by` по хешу — они получают пару
`[ключ, значение]`.

## 3. `Hash` с умолчанием: три разных вещи

```ruby
Hash.new                       # отсутствующий ключ → nil
Hash.new(0)                    # → 0, но объект умолчания ОДИН на весь хеш
Hash.new { |h, k| h[k] = [] }  # → новый объект на каждый ключ, и он запоминается
```

Вторая форма — ловушка с изменяемыми умолчаниями:

```ruby
h = Hash.new([])
h[:a] << 1
h[:b] << 2
h[:a]        # [1, 2] — потому что массив был один на всех
h            # {} — и в хеш вообще ничего не положили
```

Для чисел `Hash.new(0)` безопасен, для массивов и хешей нужна блочная форма
или явный `||=`.

## 4. `each_with_object` против `reduce`

```ruby
reduce(0)            { |acc, entry| acc + entry[:charge] }   # накопитель ПЕРВЫЙ
each_with_object({}) { |entry, acc| acc[...] = ... }         # элемент ПЕРВЫЙ
```

Обратный порядок аргументов — исторический казус, но помнить его придётся.
Мнемоника: в названии метода сказано, что делаем — «each **with** object»:
сначала то, что обходим, потом то, с чем обходим.

Правило выбора:

- накопитель **неизменяемый** (число, строка через `+`, замороженный объект) —
  `reduce`, потому что каждый шаг создаёт новое значение и его надо вернуть;
- накопитель **изменяемый** (хеш, массив, `StringIO`) — `each_with_object`,
  потому что возвращать нечего, объект меняется на месте.

## 5. Сверка двух таблиц

Задача встречается постоянно: два источника, надо назвать различия. Каркас
всегда один:

```ruby
(a.keys | b.keys).each_with_object({}) do |key, acc|
  diff = a.fetch(key, ЕДИНИЦА) - b.fetch(key, ЕДИНИЦА)
  acc[key] = diff unless diff.zero?
end
```

Три места, где ошибаются:

1. **множество ключей.** `|` — объединение, `&` — пересечение, `-` — разность.
   Для сверки нужно объединение; пересечение молча спрячет строки, которых нет
   у одной стороны.
2. **значение по умолчанию.** `fetch(key, 0)` говорит «у этой стороны ничего
   нет». `[key]` вернёт `nil`, и вычитание упадёт в другом месте.
3. **что считать результатом.** Пустой ответ = «сошлось». Это делает сверку
   пригодной для автоматической проверки: `raise if mismatch.any?`.

## 6. Порядок ключей в хеше

С Ruby 1.9 хеш сохраняет порядок вставки, и на это можно опираться: язык это
гарантирует, а не «так получается». Поэтому `group_by` отдаёт группы в порядке
первого появления, и своды выглядят одинаково от запуска к запуску — что важно
для тестов: иначе пришлось бы сортировать перед сравнением.

Множество (`Set`) и `|` над массивами порядок тоже сохраняют: `a | b` — это
элементы `a` в их порядке, затем новые из `b`.

## 7. Где это в Rails

| Ruby | Rails |
|---|---|
| `entries.group_by(&:road)` | `Entry.group(:road)` — `GROUP BY` в SQL |
| `.transform_values { sum }` | `Entry.group(:road).sum(:charge)` — одним запросом |
| `entries.map(&:cargo).tally` | `Entry.group(:cargo).count` |

Правая колонка считает в базе и возвращает готовый хеш; левая вытаскивает все
записи в память приложения. Выглядят почти одинаково — отсюда половина
медленных страниц в мире.
